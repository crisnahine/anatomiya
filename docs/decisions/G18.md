# G18

Section: G. Scope

## Decision

What a user gets is measured as the plugin on against the plugin off, on tasks whose checks a scenario file fixes before any trial runs: each arm a session with the tools a coding session has, each alone at the same leaf name, scored on what git shows it changed, and reported with each arm's Wilson interval, Fisher's exact test and what each trial cost

## Why

G5's harness asks whether the map moves one stated claim, with the plugin loaded in both arms and the tools cut to Read, Write, Glob and Grep so no shell can reach a rule file.
That is a narrower question than the one a reader of the README asks, which is what a session gets from installing the plugin: the map, the echo, the notice before a write and the reuse check at the end of a turn, in a session that has Bash and Edit.
Measured with a shell, arm B holds no map to read, so the reason the tools were cut does not apply; what does apply is that each arm sat at `with-map` or `no-map` beside the other, which a shell shows the agent, so each arm now sits alone in its own temporary directory at the repository's own leaf name.
A claim the map states as a count is scored by the map's own predicate, as G5 does, and what no dimension counts (a companion file a change ships with, an existing function the new code calls) is scored by a pattern over the files the trial wrote.
Both are fixed in `scripts/ab/scenarios/<name>.json` with the commit they were written against, and the runner refuses a clone at any other commit, so the scorer cannot be tuned to the answers after they are in; each result records the scenario file's sha256, so a reader can see the file it was scored by is the one in the tree.
A row whose predicate only counts files that already reach a translation layer gives a hardcoded string in a new file no site at all, so a scenario whose failure is that string scores it with a pattern instead, or the arm that fails would read as not judged.
A trial counts toward a check only where it did the task and the check had something to judge, so an arm cannot pass `unchanged` by writing nothing.
The first real trial on a Rails clone counted 4,362 written files in the arm whose agent booted the app, 4,360 of them bootsnap cache and a log git ignores, so a trial's work is what git would show it changed.
Its failure reason was Node's "Command failed:" message, which carries the whole argv, the prompt and this machine's plugin path among it, into a record that is committed; a reason is now the exit code and the CLI's own subtype or the first line of stderr.
Sizes come from `docs/research/what-proof-of-effect-rests-on.md`: ten trials per arm tell only a gap of about 0.7 from noise, 0.3 against 0.7 needs 24 to 29 per arm and 0.5 against 0.8 needs 39 to 45, and more tasks narrow the answer faster than more repeats of one.
A scenario whose trials take a quarter of an hour each runs as several workers on separate clones, and their raw records are joined afterwards; the scenario file is not touched once a trial has run, so a check thought of later is reported apart as exploratory.
The CLI's `duration_ms` and `num_turns` cover only the stretch after the last background notification: measured on 2.1.310, a session that waited 25 s on a background task reported 1,557 ms and one turn against 32.7 s on the harness's clock, while its cost and tokens covered the session, so a trial is timed by the harness and records no turn count.
Cost is reported beside the effect because the one controlled study of context files found pass rates unchanged and inference cost up by over 20% on average (arXiv:2602.11988).
