# B45

Section: B. Engine

## Decision

Superseded: no workflow regenerates the plugin lockfile on a Dependabot pull request. One did, `.github/workflows/dependabot-lock.yml`, and it is removed; `npm run lock:plugin` is run on the branch by hand

## Why

B35's `plugin-lock --check` fails on every Dependabot bump of a runtime dependency until somebody runs `npm run lock:plugin` on the branch by hand.
A push made with a workflow's own token starts no workflow run, so without the dispatch the pull request keeps the failed check of the commit before.
The write token lived in the one job that pushed, on a branch only Dependabot and people who can already push write to.
Superseded: `main` requires `CodeQL` and `dependency review`, both start only on a pull request or a push event, and a push with the workflow's own token fires neither, so the regenerated commit never got the two checks and its pull request could not merge.
PR #228 was the first such case and was redone by hand, as every npm Dependabot pull request before it had been.

## Status

**done** `.github/workflows/dependabot-lock.yml` is removed, and `.github/dependabot.yml` no longer points at it; `.github/workflows/ci.yml` keeps `workflow_dispatch` for a run started by hand; `scripts/plugin-lock.mjs` (`seedFor`, which leaves `libc` out of the seed) is what `npm run lock:plugin` runs.
The workflow regenerated on Node 22's npm 10, and ci checks on npm 10 and Node 24's npm 11. npm 11 writes `libc` for oxc's Linux bindings when it resolves them, which a Dependabot bump does, and keeps it from a seed. npm 10 drops it.
Measured on the first bump after this shipped: the regenerated lockfile passed under npm 10 and failed the Node 24 legs on Linux and macOS.
With `libc` out of the seed, npm 10, 11 and 12 write the same file
