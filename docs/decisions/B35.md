# B35

Section: B. Engine

## Decision

The plugin ships its own `package-lock.json`, and a plugin that declares dependencies without one is refused

## Why

Claude Code installs a plugin's dependencies itself.
Read off 2.1.251: the loader reads the plugin root with a non-recursive `readdir` and runs `npm ci --ignore-scripts` there, at a 60 second cap, where a `package.json` and one of `bun.lock`, `bun.lockb`, `npm-shrinkwrap.json` or `package-lock.json` sit together; `yarn.lock` and `pnpm-lock.yaml` are refused by name because their resolution-time hooks run around `--ignore-scripts`; a root with the manifest alone is passed over with nothing logged.
0.3.0 moved the plugin out of the repository root and left the marketplace's lockfile behind, so every version from 0.3.0 to 0.4.2 installed with no parser in it.
The evidence was on the machine and read the other way: of 26 cached versions, the 20 before 0.3.0 have `node_modules` within a second of `lib`, because the install was still firing, and only the 6 after it are minutes later, which is a separate `setup` run each time

## Status

**done** `docs/research/what-a-hook-reads-and-what-an-install-runs.md` records the doc and the build read, `plugins/anatomiya/package-lock.json`, `scripts/validate.mjs` (`dependencyInstall`, `lockfileDrift`, `INSTALLED_FROM`), `scripts/plugin-lock.mjs` (`seedFor`), `.github/workflows/ci.yml`.
Two lockfiles for one dependency set drift the moment npm resolves a range to something newer, and then the suite is green against a parser nobody running the plugin has: on the first build of this one they already disagreed, `flow-remove-types` 2.329.0 against the root's 2.328.0.
So it is seeded from the root's own resolutions rather than resolved afresh, `validate` refuses any package the two resolve differently, and `--check` rebuilds it offline, since a gate that reaches a registry fails on the network rather than on the repository.
A CI leg copies the tracked files, runs the loader's own command on them and asks `doctor`, because nothing else here would notice: every other job installs from the marketplace root's lockfile, one directory up and invisible to the loader.
On Windows the seed check says why it did not run and passes, the way the shipped-set check does and for the same reason: both spawn npm, which is a batch file there with no `.exe` for a spawn to find, and the Linux job is where either one gates.
`setup` stays, for the install that did not run or did not finish, and `doctor` leads with one line where the directory holds nothing rather than naming three engines that are absent for one reason: the rows below it then keep what was wrong with each, which differs, and drop the remedy, which does not, or the one sentence appears four times and the report reads as four faults again.
Nothing at all, and deliberately not an install that ran and stopped short: the loader kills one at sixty seconds and what that leaves is some of the packages, where the rows are the better answer because they say which.
Asked of the whole way up rather than of the directory beside the manifest, because that is where node looks: this marketplace declares its plugins as workspaces, so npm hoists every package to the root and the plugin's own directory never holds one, and a contributor whose engine failed to load was told nothing was installed and pointed at a place that will never hold it.
A resolution npm could not hoist is re-keyed to the plugin's own root rather than dropped with its workspace, and the drift gate compares against that one rather than the copy at the top, which belongs to whichever consumer won the hoist
