# E9

Section: E. Baseline and drift

## Decision

The head side of a check is read from the working tree wherever the tree differs from the commit, and a file only in the tree is examined like any other file the branch added. The base side stays on `git cat-file`

## Why

An agent writes, checks, fixes, then commits, so the natural loop runs the check exactly where it used to answer about content it had not read: a violating file planted uncommitted reported `0 MUST-FIX, 0 FIX, 0 NIT` with the miss demoted to a caveat, and the same file committed was caught (#48).
A headline that says clean and one line below it that unsays it is a headline an agent acts on.
E2 is untouched and is the reason only one side moved: the baseline population is still read at a commit, so no edit of the agent under review can move the bar it is judged against.
The cost is that a run is no longer reproducible from git alone, so the report says how many files it read that way

## Status

**done** `changeset.mjs` (`pendingPaths`, `withPendingEdits`), `check.mjs` (`treeSource`), `plugins/anatomiya/commands/check.md`.
Whether a pending path has a base version is asked of the merge base rather than of the index letter: `git rm --cached` and a delete-then-restore both report an addition for a path whose committed version is right there, and read as new every site in the file was charged to this branch.
What that cannot answer is a file moved to a name it never had and not yet committed, because `git status` rename-detects nothing for an untracked path; the move is judged correctly the moment it is committed, where `--find-renames` sees it.
The note it replaces said what the check could not see, and now says it only where the tree is not read: with no merge base nothing can be called newly introduced, so the pending files are named rather than judged
