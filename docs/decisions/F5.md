# F5

Section: F. Safety

## Decision

Any subprocess: `execFile`, arguments after `--`, reject paths starting with `-`, cwd outside the repository, no network, timeout, streamed stdout byte cap

## Why

Measured: `--` neutralises the whole argv class; a tracked file named `--instruction-file-path=.git/config` exfiltrated a secret without it

## Status

**done** `git.mjs` (`FLAGS`, `refuse`, `gitEnv`), `pool.mjs`, `ruby.mjs`.
Two runners, one buffered and one streamed (F6), and both carry the timeout and a byte bound.
Every git call goes through one of them: `corpus.mjs` and `authors.mjs` were the last two running their own `spawn`.
One thing reaches the network and it is not the scan: on a shallow clone the check fetches the single base commit, because `merge-base` cannot answer without it and the alternative is reporting a branch against nothing.
`ls-remote` and `fetch --depth=1` are the whole of it, both on that one path, and F14 separately forbids the lazy-fetch a partial clone would otherwise trigger.
The scan makes no outbound call at any point, and the `gh` measurement helper that did was published in `lib/`, imported by nothing, and is gone.
`--` is still not universal, because `rev-parse`, `cat-file`, `merge-base`, `config` and `status` do not take it, so the rule is stated from the other side instead: an argument that reads as an option must be one this tool wrote, checked against a closed list of the flags it actually passes.
A ref, a sha or a path that begins with a dash now refuses the call rather than resting on whichever predicate was supposed to have caught it.
The two subprocesses that are not git carry the battery too: `ps` runs with a timeout, a kill signal and a byte bound, since `execFileSync` blocks the parent's event loop and a `ps` that never returns is the memory guard becoming the hang; `ruby.mjs` no longer refuses a leading-dash path: paths reach the child on stdin and never in argv, so the rule has no argv to guard there, and the refusal charged a 16-byte `-weird.rb` as over the size cap and as an answer from an interpreter that never ran.
`ruby.mjs` times the wall clock behind the idle window, since a child answering one file every fourteen seconds never trips a liveness check.
`ps` runs by the absolute path `/bin/ps`, never through PATH: `scan .` runs from the repository, and an empty PATH entry ran a `ps` the repository committed.
Linux does not run it at all and reads `VmRSS` from `/proc`, which slim images without procps also have.
Both parser bridges now run outside the repository.
That is also why the Ruby that parses is the one `ruby` answers from the temp directory, with the version-selection variables dropped: a `.ruby-version` or `.tool-versions` in the repository, or an `rbenv shell` choice, does not pick it.
`PATH` is cut to its absolute entries too, because the command is looked up on the child's own `PATH` and an empty or relative entry resolves against that world-writable directory: a trailing colon on a machine with no Ruby ran another local user's planted `ruby` (B42).
Resolving from the repository root was declined.
A version file is the repository's to write, and asdf reads a `path:` version as a directory to run the interpreter out of, so the resolution itself could run a binary the repository ships.
The README says so, and `test/ruby.test.mjs` pins that the prism listing, the readiness probe and the parser all start outside the repository., and git carries an environment that refuses a credential prompt.
It also turns off the commands a repository's own `.git/config` can make a read run: a tarball carries that file, and `core.fsmonitor` set to a script ran on every `status` this tool made.
`gitEnv` appends `core.fsmonitor=false` and `core.hooksPath` at the null device as `GIT_CONFIG_COUNT` entries, which every subcommand honours above every config file, after any a caller already carries.
`log.showSignature` and `fetch.recurseSubmodules` go off the same way: the first made every `log` run the repository's `gpg.program`, and the second runs git inside a submodule under a config this process never read.
The commands whose names are the repository's own are closed per repository instead (`repositoryCommands`): one `git config --show-scope --null --get-regexp` per root per process reads which of `filter.<name>.clean`/`smudge`/`process`, `core.sshCommand`, `core.askPass`, `core.gitProxy`, `core.alternateRefsCommand`, `remote.<name>.uploadpack` and the credential helpers the repository's own files set, and each is replaced after the fixed entries by the user's own global or command-line value where there is one: an empty filter with `required` off (measured: git then reads the file as its bytes, and without `required` off refuses it), `ssh` or the user's `GIT_SSH`, an empty askpass, `true` for alternate refs, and the helper list emptied and refilled with the user's helpers.
A value the person set at the repository's own scope is replaced as well, since nothing tells it from one a tarball shipped; `SECURITY.md` says to set it globally.
Three are first-match-wins and cannot be replaced by a later entry, measured: an upload-pack is named on the `fetch` and `ls-remote` command line, and a partial clone's lazy fetch, git's own child with no command line of ours, is not made for a repository naming one (measured: the repository's script ran on the check's rename diff), a repository naming its own `core.gitProxy` has `git://` closed, and `status` and `diff` pass `--ignore-submodules=dirty`, since a submodule's dirtiness is asked by running git inside it under its own filters and a `submodule.<name>.ignore=none` in `.git/config` outranks every config default.
A config git will not read refuses the call.
Every vector is pinned against a control where plain git runs the same script, on git 2.43 and 2.51 (`test/git.test.mjs`), and a user's global `core.sshCommand` and credential helper still run.
The cost is one `git config` per repository per process (the Stop hook measured the same within noise).
The exact commands `git lfs install --local` writes are left alone, since they run the user's own installed `git-lfs` and replacing them made every LFS file whose stat moved read as changed; any other command under the `lfs` name is replaced like the rest. git-lfs reads the repository's config too and runs an `lfs.extension` clean or smudge command, a custom transfer's `path` or a standalone transfer agent named there, so a repository naming one gets its `lfs` filter emptied, the user's global one included.
A standalone agent or custom transfer the person set up in the repository's own config is emptied with it, so an LFS file whose stat moved reads as changed and `pin` refuses the tree; set it globally.
One command installs anything and no other command runs it: `setup` reaches a package registry with `npm install --omit=dev --include=optional --ignore-scripts --no-audit --no-fund`, `cwd` the plugin root, so a scan, a check and a pin install nothing and the shallow-clone fetch above stays the only outbound call any of them makes (B23)
