# H40

Section: H. Layout

## Decision

A hook answers from the repository the tool call is about, and from the working directory only where the call names no place

## Why

Both hooks resolved by walking up from the process working directory, which says where a shell happens to be rather than what the call is about.
The walk stops at the first map it finds, so it is right going up and blind sideways: two checkouts under one parent served each other's roster and each other's directives, under the line saying it was counted from this repository's own code.
The boundary that would have stopped it sits under the other checkout, which the walk never visits.
Measured on 2.1.251 off captured payloads rather than off the tool definitions: five tools name a place, `Read`, `Write` and `Edit` under `file_path`, `NotebookEdit` under `notebook_path`, `Glob` and `Grep` under `path`.
One walk serves all three shapes rather than a branch per tool, since a file answers with its parent, a directory with itself, and a path a write is inventing with the nearest ancestor that exists.
Taking the parent of a directory would have been the same bug once more: a `Glob` at a repository root would answer from the directory holding every checkout.
`Bash`, `Agent`, `WebFetch` and `ToolSearch` name nothing, and for `Bash` no field anywhere locates a `cat > file`, so the working directory stays the answer there and for a shell it is the right base anyway.
That directory is read off the payload rather than off this process: it follows the agent, and one `cd` moved it for every payload after with nothing telling the hook.
A relative path is read against that same base, because the tool read it against that one and nothing normalises `tool_input` on the way here; `targetIn` reads it against the base `aboutDir` used, or the two disagree about one payload and the hook says nothing about a write it has already located.
Two outcomes change beyond the defect, and both are named here rather than left to be found.
The issue called it right that a parent session gets nothing, and it no longer does: a real payload always carries a `cwd`, so the only silence left is a payload holding neither a path nor one of those.
For a shell that is an improvement, since its own directory is the correct base.
For an `Agent` call it means a subagent's first map is picked by wherever the parent's shell last was, which is this defect's own shape one level up and is why the payload's field is preferred to the process's.
And a call naming a file in no checkout at all leaves the session's map standing rather than blanking it: reading a system file or another project's is ordinary, and answering nothing there takes the map off a turn that had one.
The test is whether the call has a checkout, not whether one answered.
A first draft fell back whenever no map came back, which reads three different answers as one and gave a nested repository with no map, and a mapped sibling whose map is empty, the enclosing checkout's counts: the exact thing the boundary walk exists to refuse, re-created by the fix that was meant to stop it.
A repository that has nothing to say says nothing, and only a path belonging to no repository is answered from somewhere else.
The tradeoff the issue asked to be weighed, that a session can be handed two maps in two turns, is now more frequent and not less: before, only a `cd` moved it, and now every read across a repository boundary does.
That is the point rather than the price, since the map that arrives is about the file that arrived with it, and the alternative measured worse: one map per session is the wrong map for every call outside it.
Each stamp names the checkout it was counted at, so two maps in one session can be told apart.
The digest stays the body's, since two maps with one body state the same things.
The walk is refused above 4096 bytes, which no filesystem can hold: it costs a stat and a copy per segment, and a payload inside the megabyte this reads held 400,000 of them and took 7.8 seconds against the 5 the declaration asks for, losing the turn its map and burning the budget before every tool call.
The bound sits on the path the walk runs on rather than on the field it came from, since a first draft gated the target alone and a short target with a long `cwd` in the same payload went round it at 10.5 seconds.
`targetIn` takes the same bound one segment deeper, where `resolveLinks` recurses per segment and the same payload overflowed the stack rather than costing seconds.
