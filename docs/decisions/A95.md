# A95

Section: A. Delivery

## Decision

The map refreshes itself: a `refresh` hook on `SessionStart` and `FileChanged` names the checkout's `logs/HEAD` and `HEAD` as absolute `watchPaths` and starts a detached worker, which rescans only when a stamp moved: HEAD, the index, the pin, the build, whether the repository holds packages, which of `tsconfig.json` and `tsconfig.base.json` the root is read through, and where `typescript` resolves and its `package.json`

## Why

The map was a snapshot of one working tree with nothing on disk saying which, so every checkout, pull and commit left it describing another tree until somebody ran `scan` again, and users re-ran it on every branch change.
Read off build 2.1.283 (`docs/research/when-a-hook-can-refresh-the-map.md`): CLAUDE.md and unconditional rules are read concurrently with SessionStart and memoized, so a synchronous scan at start misses the session it delays; plugin `FileChanged` matchers never register a watch, only `watchPaths` do, and the list is replaced by whichever hook answers last; a hook is pending until its pipes close, with the timeout disarmed once its process exits.
So the hook does no git work, re-names its watches on every answer, and the worker runs with every stdio closed.
Scoped to a checkout with a map of its own (A24), or, where the session's directory has none, each checkout directly below it that has one (A99): the first scan is the opt-in.
Moving a stale lock aside to take it over let two workers hold the lock: 2 holders in a forced interleave of three, and 1 of 200 rounds at 3 workers and 11 of 200 at 8 started together, against one holder in 200 of 200 through the lock token (A117)

Left alone: a map, a `baseline.json` or any file of `.claude/anatomiya/` the repository tracks (a committed pin can never name the commit that holds it, and following the tip rewrote it on every refresh; the lock and `refresh.again` are removed after use, and removing a tracked one is an edit `pin` then refuses), and a merge, rebase, cherry-pick, revert or bisect in progress.
The rescan decides whether to run the checker the way any scan does (B7), with one exception a scan run by hand never takes: a degraded verdict measured under the same build, packages and root config is carried into the new map and the checker is not run, as is a failed run's from the second in a row under them (B8).
A Cursor or Copilot copy of the map (`scan --targets`) whose overview the repository tracks is left alone by that rescan while the rest is written (`committedTargets`, and `leaveAlone` on `writeMap`): nothing there is written, removed or turned off, and the record keeps the names it had.
Stopping the whole refresh for a tracked copy was measured with the Cursor overview tracked and the `.claude/rules` map ignored: the refresh rewrote nothing, so the map Claude Code reads stayed a commit behind, and committing only the copy another tool reads from the remote is the likeliest use of one.
Measured with the copy left alone, on a repository that commits only `.github/instructions`, after a commit that added a third area: the refresh rewrote the `.claude/rules` map and the uncommitted Cursor copy, left the three Copilot files as committed, and `git status` stayed empty.
A copy left alone prints no line and no JSON key.
Where git could not say whether the overview is tracked, the copy is left alone too.
A scan run by hand leaves nothing alone and rewrites it, so a committed copy is as stale as its last scan by hand, which is what a committed `.claude/rules` map already is.
A failed rescan keeps the previous map (A13), is retried after 30 minutes, and is said once in the delivered map until a refresh or a scan run by hand succeeds; a scan run by hand records its stamp, so the next refresh has nothing to redo.
A rescan that wrote the `.claude/rules` map and left a Cursor or Copilot directory stopped at a locked file (A104) is no failure: `refresh.json` keeps `ok: true` and names the directory under `stopped`, a key a build that does not know it reads past, and the same stamp is due again after the same 30 minutes for as long as a directory stays stopped, and no more often.
Measured with a rename onto Cursor's overview answering `EBUSY` once: without the key every later refresh at that stamp answered `current` and the Cursor copy stayed one map behind; with it the refresh after the 30 minutes wrote that directory and the key was gone.
A directory with no write permission is named under `stopped` too, since the key reads `unwritable` on the plan (`stoppedIn`) and the audit sets that as a locked file does.
Measured with `.cursor/rules` at mode 555 and the target on: four refreshes 31 minutes apart ran four scans, each a whole scan, with the type checker unless the last verdict was degraded and is carried, and the `SessionStart` answer carried no `systemMessage`.
What ends it is the directory's mode fixed, which the next of those scans writes through, or a scan run by hand, which prints the reason and records its stamp with no such key.
Turning the target off does not, since `scan --targets claude` refuses while the directory cannot be written: `.cursor/rules is not writable, so the map could not be written: fix its permissions and scan again`.
The `FileChanged` group is matched on the basenames the watches have, and a change to any other file answers `{}`: the watch list is one list shared by every hook, and answering another plugin's file replaced its watch with ours.
The stamp streams `ls-files -s` (F6).
An exclusive lock, created whole by a hard link, or by an exclusive create where the link is refused, and a 20 minute clock on the worker (F5).
A lock whose owner is gone, or which is older than half an hour, is taken over by the worker that wins the exclusive create of the lock token `refresh.lock.<the dead lock's nonce>`: it removes the lock only while the lock still holds the content judged dead, and every worker then makes the one create (A117).
A lock token a worker was killed holding is broken by the next worker where its mtime is more than 62 s from the clock, under `refresh.lock.<nonce>.<the token's mtime in ms>`, and one nearer the clock is left alone, since its breaker may still be running.
The worker that takes the lock removes every lock token beside it that names another generation.
What this leaves: a worker killed while it holds a token's own token leaves a dead lock no worker breaks, every refresh worker in that checkout then leaves `refresh.again`, answers `busy` and scans nothing, and it stays so until a scan run by hand there sweeps the token's own token (A118); nothing says so meanwhile, neither `doctor`, the summary nor the delivered map.
An entry at the lock's name that is no lock is told apart from a lock taken: an empty directory is removed and that refresh takes the lock, and any other entry there that is no regular file and that the system will not remove answers `lock-blocked` with the path as `blocked`, at the first take and at the take after a round, so nothing is scanned without the lock.
A lock file the system will not unlink answers `busy`, since Windows refuses one a handle still holds open and the next call finds it free.
The worker's answer reaches nobody, its stdio being closed, so a scan run by hand says it: where a directory holding entries is at the lock's name the plan carries `lockBlocked`, the JSON summary too, a dry run included, and the summary prints `".claude/anatomiya/refresh.lock" is a directory holding entries, so the map is not refreshed in the background in this checkout while it stays: remove it`, and removes nothing.
Measured on macOS, a fifo, a socket, a link to a file, a link to a directory holding a file and a dangling link at that name are each unlinked and the lock taken on that call, so the line is printed for a directory holding entries alone.
Where there is no reflog to watch, the watch names what every move rewrites instead: `reftable/tables.list` on the reftable backend (measured on git 2.51, where a commit replaces the file and no `logs/` exists; a reftable clone also writes the remote-tracking ref an entry with an empty message, so the made-here walk reads no remote-tracking ref's entries, which a fetch, a push, a clone or a hand write moves and no commit is ever made on; `test/refresh.test.mjs` and `test/reuse.test.mjs` run a real reftable repository where git is 2.45 or newer), and the index in a files repository created without a reflog, the last resort because `git status` rewrites it too and each costs a worker that finds the stamp unchanged.
A linked worktree on reftable keeps its HEAD and that HEAD's log in a stack of its own, so its `reftable/tables.list` is watched beside the shared one: a commit on a detached HEAD there rewrites nothing else.
The `FileChanged` matcher is `^(HEAD|index|tables\.list)$`, anchored, since a matcher holding a dot is compared as an unanchored RegExp.
A lock is released only while its content is still the worker's own.
It is read bounded and typed, since the directory can come with the repository: a lock planted as a link to `/dev/zero` read whole never returned, and the worker's clock never fired, since the read held the one thread it would fire on (measured 2.17 GB in 8 seconds).
One stamped later than now is stale.
A worker that finds the lock taken leaves `refresh.again`, and the holder reads it after letting go and runs again: without it a move landing after the holder's last look at HEAD, or past its three passes, waited for the next move.
A record below its checkout's root (a copied project's `.claude/`) refreshes nothing: the scan it would start writes at the checkout's root, which never opted in.
A change to any file the watch could name in this checkout's git directories is answered, and the current watch named again, so the watch moving off the index at a first commit does not end the session's refreshes.
