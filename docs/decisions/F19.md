# F19

Section: F. Safety

## Decision

An explicit `--base` that resolves nowhere is refused, and `HEAD` is refused before anything is fetched

## Why

The command file's own contract is that a non-zero exit means the check could not run, show its output and stop.
`--base no/such/ref` was answered with 685 added-lines findings over 2,150 files at exit 0, which an agent is told to trust as a finished review of a branch that changed nothing, and the same degradation happens on an ordinary full clone where the fetch fallback never runs.
`--base HEAD` resolves locally in every repository that has a commit, so reporting it as a base a shallow clone could not fetch names a cause that is not the reason and a fix that would not work; it is refused for what it is, this branch's own tip, and refused before the shallow fallback, which fetches by branch name and would otherwise use a remote branch literally named `HEAD` and defeat E6.
A ref this tool guessed is a different question from one somebody typed: the candidate list not resolving is a repository that keeps its trunk somewhere else, which is what the added-lines degradation is for, and it is unchanged.
A repository with no commits at all has no ref to mistype against and still answers that nothing was examined.
Every other spelling of this branch's own tip is refused the same way once it resolves: `HEAD~0` and the branch's own name compared the branch with itself and printed a clean report at exit 0.
Two spellings of that commit stay bases, because each names something other than this branch: another branch at the same commit, and the commit by its id, which is what a branch holding only uncommitted work is checked against.
The branch's own name is refused only where the base the check would pick unasked is somewhere else; on the trunk, with uncommitted work, it names the base the check would have picked anyway

## Status

**done** `check.mjs` (`resolveBase`, `refusal`).
