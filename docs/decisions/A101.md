# A101

Section: A. Delivery

## Decision

The scan writes the record's `layout` a second time, alone, as `.claude/anatomiya/layout.json` holding `{ schema, record, layout }`: the record's own schema, and in `record` the size and mtime of the record file it was taken from, read off the record's temporary file before the rename, which keeps both. It is staged with `facts.json` in the same replace, so a failed write puts both back. The record put back is a new file with a new mtime, so where the old layout file answered for the old record, the rollback writes the pair again through `writePair`, the layout file stamped from the restored record's temporary file and under the old layout file's own schema, since that scan wrote the record put back. A record that could not be read before the replace has no bytes to put back, so it is left as it is and not written again. `writeFacts` writes through `writePair` too: both temporary files before either rename, both removed on any failure, and the record renamed first, so a failure at the record's rename leaves the old pair whole and still answering, and one at the layout file's rename puts the record back the way the rollback above does. The commit calls `writePair` once more where a Cursor or Copilot directory was put back alone, to write the record with the names that directory had before (A104), and once more after its last removal where the record listed files to remove, to write it without them (A13). The hooks read it only where its schema is one this build reads, the record on disk has exactly that size and that mtime, and that size is within what the record reader takes, and read the record otherwise. A layout file that answers is believed when its layout is null too, without reading the record. No schema bump

## Why

The notice, the end-of-turn check and the refresh parsed the whole record to read its layout: 10,217,406 bytes on microsoft/vscode for 2,037 bytes of layout.
A map written before this file existed has no layout file and is answered from the record as before.
The stamp has to name the one record file, not a kind of record: a length alone passed a committed record with a conflict marker refused by the reader, and length and age together still passed a commit that changed `facts.json` and not `layout.json`, checked out with the layout file landing last, and any restore that keeps mtimes (`cp -p`, `rsync -a`, `tar`).
A record past the reader's 64 MiB cap reads as nothing, so the layout file is refused there whatever its stamp says.
Anything the stamp refuses goes to the record, whose answer is the one main gives.
A `.claude/` the repository commits carries `layout.json` too, and it is inert after a clone: its stamp names an mtime the clone's record does not have.
So a committed map never takes this path after a clone or a checkout that rewrites the record, since the record's mtime is then the checkout's and the refresh leaves a tracked map alone (A95), and it answers from the record: correct, and as slow as before.
Measured on that record, written by this build's scan into a scratch repository, 15 alternating runs each at load 4.5 to 4.6 with bare node at 25.1 ms, medians: a notice that reads its rules took 89.8 ms on 0.13.3, 60.1 with A100 alone (the same record, no layout file) and 41.1 with this, and its peak RSS went 88.0 MB, 81.7 and 51.0.
Hook answers are byte-identical to 0.13.3 on the same payloads, with and without the layout file.
What the stamp cannot tell apart: on a filesystem with coarse mtimes (FAT 2 s, HFS+ and ext3 1 s, some SMB mounts), two records of the same size written in the same tick share a stamp, so a record replaced that way by something other than this writer reads as the one the layout file was taken from
