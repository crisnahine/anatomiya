# B81

Section: B. Engine

## Decision

In a file that may hold JSX, a line the JavaScript line rule reads as a comment asks where it opens with `//` or `/*`, holds an expression in braces, and is no doc comment: inside JSX children both are text, and the braces run

## Why

The line rule reads no tree, so `// {items.reduce((s, i) => s + i.price, 0)}` inside a `<p>` read as a comment and asked nothing: run as the hook, adding that line to a `.jsx` file answered `{}`, and the same line without `// ` blocked.
A parse would tell text from a comment, and oxc in the hook's own process can end it with an uncatchable SIGSEGV (`parse.mjs`), so the rule reads the line instead.
Measured on excalidraw's `.tsx` and `.jsx` files: 3 lines open like a comment and hold an expression in braces, all real comments, which is the false ask this costs.
A `.jsx` or `.tsx` file may hold JSX, and so may a `.js` file that holds a closing or a self-closing tag, where a `.ts`, `.mjs` or `.cjs` file cannot; a comment with empty braces, as commented-out code writes `{}`, and a doc comment's `{string}` still ask nothing.
The braces are read from each `{` to the next brace, so a line of braces never closed costs its length: one pattern over the whole line took 700 ms on 2,500 lines of `// {a{a...`, most of the stop's one second.
What this gives up: the later lines of a `/*` opened in JSX text are still read as a comment, as they were (A91)
