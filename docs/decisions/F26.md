# F26

Section: F. Safety

## Decision

A timing test asserts how the work grows, never a wall-clock budget

## Why

Three linearity cases asserted milliseconds.
The introduced case took 8.4 to 15.6 s on a loaded machine against its 6 s budget, and the quadratic code it guards takes about 12 s at the test's size, so the bound could not tell a slow runner from the regression.
The size cap in B3 already replaced a parser timeout for the same reason.
The test now times n and 2n in CPU time, interleaved, fastest of several rounds, so noise only adds time.
It refuses a ratio of 3 or more: linear reads about 2, quadratic about 4.
Each case was checked by putting the quadratic code back: 3.93, 3.93 and 3.55.
A read of 3 or more is taken again, up to three reads, and the smallest stands: on the CI runners linear work read past 3 now and then, 3.10 to 3.51 on six tests, and under it on the run's other legs and in later runs, while quadratic work reads about 4 (`docs/measurements/2026-10-12-growth-reads-on-runners.md`).
Running both sides equally long was measured and refused: over 156 paired reads its tail was longer, 3 reads past 3 against 1
