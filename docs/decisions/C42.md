# C42

Section: C. The counted-claim model

## Decision

`migration_reversible` counts no migration whose forward method, or a method of the class it calls, holds a command `change` cannot invert, in the form ActiveRecord's CommandRecorder refuses, spelled directly, through `change_table` or through `send`. SQL through `exec_query`, `exec_update`, `exec_delete`, `exec_insert` or a bare `update`, `delete` or `insert` handed a string is read as `execute` is. A scoped constant under ActiveStorage, ActionText or ActiveRecord is data work only as the receiver of a data call, and a model handed on is data work only where it reaches one: as an argument or keyword value of one of the class's own methods whose parameter receives a data call, as a local's value, a multiple assignment's value or an iterated array's element whose name receives one, or as an argument of any other call whose block sends one to a local. Both rows read one body: the methods Rails runs and the class's own methods they reach

## Why

C21 excluded data migrations because `change` auto-inverts only a closed set of commands, and applied it to unreadable SQL only: `change_column` in `change` conformed though its rollback raises IrreversibleMigration, and the up/down form of it got a FIX.
`ActiveStorage::Blob.update_all` and `ActiveRecord::SchemaMigration.delete_all` read as framework because FRAMEWORK was matched on the root segment.
ActiveRecord also names the connection, `transaction` and its errors, and ActiveStorage and ActionText name a table read for DDL, so under all three only a scoped constant receiving a call from a closed list (`where`, `find_each`, `update_all`, `delete_all` and the other finders and writers) is a model, and `ActiveRecord::Base.connection` stays framework.
Read as a model whatever was sent to it, a scoped ActiveStorage or ActionText constant made `add_column ActiveStorage::Blob.table_name, ...`, `ActiveStorage::Blob.reset_column_information` and `add_index ActionText::RichText.table_name, ...` data work, and reading every constant argument as a handed model did the same to `default: Kind::Basic`; `check` then gave each pure schema migration a FIX that 619e9a7 did not, so a handed constant that reaches no data call decides nothing.
`exec_query` and its siblings reach the connection through CommandRecorder's method_missing unrecorded, so a rollback re-runs their DDL, and `send(:change_column, ...)` raises IrreversibleMigration as the plain call does.
Rails runs `change` and never `up` when both exist, so `change` is the body read.
The refused set and the data calls are read off activerecord 8.1.4's source, not recalled: every command in `ReversibleAndIrreversibleMethods` with no `invert_` method (`execute`, `change_column`, `add_enum_value`) and every `invert_` that raises (a constraint or enum dropped without its expression, columns or values, a from:/to: pair missing, `add_unique_constraint` with `using_index:`, `drop_virtual_table` with no values), through `change_table`'s `Table` too; the data calls are `Querying::QUERYING_METHODS`, the SQL finders, `all`, `unscoped`, Persistence, CounterCache, and the instance writers reached through `new(...).save!`.
The two readers disagreed: `holdsIrreversible` read only the forward def and `dataWork` the whole class, so a `change_column` in a helper `change` calls conformed.
Measured 619e9a7 against this build on 14 Rails corpus clones, db/migrate only, `migration_reversible` then `migration_schema_only`: empire-flippers/api 1097 of 1130 to 1008 of 1017 and 1130 of 1525 to 1128; discourse 778 of 969 to 721 of 781, schema-only unchanged at 969 of 1719; forem 821 of 938 to 778 of 853; consul 547 of 600 to 547 of 562 and 604 of 606 to 603; mastodon 381 of 454 to 379 of 423; openfoodnetwork 138 of 174 to 133 of 144 and 174 of 259 to 171; whitehall 96 of 124 to 96 of 113; plots2 35 of 78 to 30 of 63 and 78 of 103 to 77 of 102; openproject 78 of 85 to 78 of 80 and 85 of 141 to 84; huginn 31 of 38 to 29 of 33; canvas-lms 47 of 61 to 47 of 56; diaspora 18 of 22 to 17 of 18; decidim and errbit hold no migration class.
Every file that moves on the reversibility row leaves its population, and none changes side; every file that moves on the schema-only row is an ActiveStorage backfill, a model handed to a helper or a batch block, or plots2's backfill, which `exec_query(sql)` now drops from both rows as an unreadable `execute` would.
Neither regression shape occurs in the corpus: the build before this fix measured the same figures except on three files, huginn's array of models read for their columns, which it counted as data work, openproject's `in_configurable_batches(Query) { ... update_column ... }`, which it missed, and plots2's `exec_query(sql)` backfill, which it counted on both rows

## Status

**done** `dimensions-rails.mjs` (`ownMethods`, `eachRun`, `holdsIrreversible`, `refused`, `TABLE_COMMAND`, `SEND`, `sqlCall`, `dataWork`, `handed`, `dataCallOnLocal`, `argValues`, `built`, `isModel`, `FRAMEWORK_MODELS`, `DATA_CALLS`), pinned by `test/dimensions-rails.test.mjs` and `test/applicability.test.mjs`.
The C39 witness gate still drives only bare FRAMEWORK roots; a scoped ActiveStorage, ActionText or ActiveRecord control is covered by the new applicability witness.
A model reached through a string or a method is not read: `"User".constantize`, `const_get` and `def model = User` decide nothing.
A model held in an instance variable (`@model = User`) is not followed, since only locals and parameters carry a name this reads.
`m ||= User` is not read as binding `m`, only a plain or multiple assignment is.
The keys of a hash literal (`{ User => true }.each { |k, v| k.update_all(...) }`) are not bound to the block's parameters, only an array literal's elements are.
Names are matched across the methods read, not per method, so a same-named local elsewhere receiving a data call makes a handed model data work.
A constant handed to a method outside the class reaches a data call only through that call's own block, so `backfill(User)` from an included module decides nothing.
Row-writing SQL through a bare `update`, `delete` or `insert` is read only when its first argument is a string or a call on one, and an `exec_query` or sibling whose SQL cannot be read drops the class from both rows as an `execute` does.
Only the class's own methods are followed, called by name, through `self.`, `method(:x)` or `send(:x)`; a method from an included module or a base class is not read, code in the class body outside any method is read by neither row, and a helper nothing calls is read by neither.
A command sent to any receiver other than a `change_table` block's parameter, such as `connection.change_column`, is not judged.
The migration's version is not read: before 5.2 Rails inverted a comment change with no from: and to:, and this row refuses it at every version.
`remove_check_constraint` and `remove_exclusion_constraint` with `name:` alone pass Rails 8.1's own size check and then fail on rollback building the constraint with no expression, so they count as refused.
A call added to ActiveRecord after 8.1.4 is not a data call until the list is re-read.
A constant handed as an argument is read inside a method or a block, and never in the class body's own statements; handed to `revert` or `migrate` it reaches no data call and decides nothing: read in the class body, `include Mastodon::MigrationHelpers` took 5 of mastodon's schema-only migrations out of both rows, and `define_method(:up) { backfill(User) }` is a body that runs.
`remove_column` and `drop_table` count positional arguments as Rails 8.1 does, so `if_exists:` alone is not a type or an option, and a string key such as `"force" => :cascade` is one
