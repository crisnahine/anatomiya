# E10

Section: E. Baseline and drift

## Decision

One reader hands both the check and the baseline the content at a revision

## Why

Each answered the question itself and the two disagreed about what an unreadable path means: the baseline wrote a temporary tree and handed back paths, the check read one blob at a time into strings and let the parser write them out again, serially.
Measured on a 40-file branch: 80 of the 88 git processes the check spawned were `cat-file` waiting on each other.
Re-measured on this repository, which examined 59 files and read 99 blobs: 107 processes of which 99 were `cat-file blob`, the same before and after, and the run went from about 2.1s to about 1.25s, roughly 40% off a check.
Those were one process per blob, read eight side by side; one child per call answers them since (E17)

## Status

**done** `revision.mjs` (`readAtRevision(root, sha, files, {withSource, timeout, lazyFetch})`), `git.mjs` (`blobReader`), `check.mjs`, `baseline.mjs`.
Through disk because the parser runs out of process and takes a path (B5), and `withSource` for the caller that also needs the bytes in hand, since the check quotes snippets and resolves line numbers against them.
A path that will not come back is reported rather than thrown on: one missing file is one file to both callers rather than the whole set.
The clock travels with the caller, or the check's blob reads would silently move from its own 30s clock to the scan's 120s one.
The size cap does not: `blobReader` and `showBlob` give up at exactly the size the parser skips at, so a blob refused there is one the parse would have refused anyway, and no caller can widen it.
The check names such a file as the parse would have, `head-oversize`, from `readAtRevision`'s `over size cap` reason, and the working-tree read says the same of a file past the cap; both had read as `head-unreadable`.
E2 is untouched: the base side is built from the pre-rename path and read at the merge base, so no working-tree path reaches it
