# D15

Section: D. Gates

## Decision

The authors walk (D5) and the co-change walk (F27) replay each commit's record from a history store, `.claude/anatomiya/history-authors.gz` and `history-cochange.gz`, and ask git only for the order of the commits and for the commits the store lacks. A store is used only under a stamp of everything a commit's record depends on besides the commit, and a store or a stamp that cannot be checked is the full walk, never an error

## Why

Both walks read every commit they cover on every scan, 63,494 on discourse and 145,780 on vscode for the authors, though a commit that lands changes what no other commit's diff says.
Measured after one new commit, the two walks alone with the store's write, medians of five interleaved runs in fresh processes: 6.03 s to 2.63 s on discourse at a load average of 37 falling to 21, and 9.42 s to 3.50 s on vscode at 16 to 32.
A scan that finds no store pays the write on top of the full walk: 6.25 s on discourse and 9.94 s on vscode in those runs, about 0.3 s more.
What is left of a replay is mostly the order: on discourse the store inflates in 68 ms, its digest takes 20 ms, splitting every record 90 ms, and `git rev-list` 1,010 ms.
The order is asked of git on every scan because a merged branch lands its commits among older ones, and a reader that follows renames answers differently for another order: a store taken 30 commits back on openproject had 162 commits to read.
Stores taken at HEAD~1, HEAD~30, HEAD~300 and HEAD~3000 and replayed at HEAD on discourse, vscode and openproject gave 24 of 24 answers equal to the plain walk's, every key, every set and the insertion order, and again at HEAD~30 on discourse and vscode under the stamp this row describes: 63,464 and 145,750 commits from the store, 30 from git.
The plan of all 60 corpus repositories is the one 0.15.1 writes.
gzip at level 1 because the write is paid on every scan that met a new commit: discourse's 32.7 MB of authors records pack in 235 ms to 6.1 MB at level 1 and in 792 ms to 5.1 MB at level 6.
The stamp holds what was measured moving a record with no commit moving.
`diff.orderFile` changes the order git prints a commit's rows in, and so the order the map's entries are made in.
A `-diff` attribute on a 40-line CRLF file renamed with 16, 18 or 19 lines edited turns its `D` and `A` rows into `R057`, `R052` and `R050` on git 2.54, from an untracked `.gitattributes` at the root as readily as from a staged one, and from a branch `GIT_ATTR_SOURCE` or `attr.tree` names once the branch moves.
Only a digest of the configuration is stored, since the configuration names paths and can hold a token, and the store sits in a directory a repository may commit.
The stamp starts 6 git processes and reads 9 files on discourse and 11 on vscode, in about 25 ms: medians of five runs at a load average of 7 were 23 to 33 ms.
Both walks with their stores in place start 14 git processes.
Whether the clone is partial picks `-M` or `-M100%` (F14), so it is part of the walk's arguments and of the stamp, and it is read as git reads it.
git 2.54 refuses `08`, `2g` and `" true"` as a boolean and its `log` dies on them, and a blobless clone whose promisor flag reads `true` and then `false` still fetched from its promisor.
On one measurement pass, at a load average of 30 to 190, 13 of 15 scans of a blobless vscode clone gave 37,970 author paths where 41,954 are right, which is the walk's answer with the flag read as unset; it did not recur in 29 further scans, and a git that cannot be asked is unread history since.
Given up: a `.gitattributes` below the root that git does not track, which only a walk of the tree finds, and the system-wide attributes file on a git older than 2.42, which cannot name it, are not in the stamp, so a store taken under either keeps its rename pairing until something else moves the stamp.
Given up: where the commits are intact and a tree or a blob was lost after the store was taken, the plain walk would say the history could not be read (F13) and the replay answers from the store, with what git printed for those commits under the same stamp.
Given up: past 256 MiB of records, about 520,000 commits at discourse's 515 bytes each and 860,000 at vscode's 313, nothing is stored and the full walk answers every time.
On Windows the user's attributes file is not watched where `HOME` is unset and `HOMEDRIVE` with `HOMEPATH` names another directory than the one Node answers, read in git for Windows' source and run on no Windows machine

## Status

**done** `history.mjs` (`historyFields`, `saveHistory`, `HISTORY_FILES`, `HISTORY`, `openStore`, `stampOf`, `readBesides`, `replayable`, `configValue`), `authors.mjs` (`authorsByFile`, `logStream`, `isPartialClone`, `gitBoolean`), `cochange-walk.mjs` (`walkCochange`), `commands.mjs` (`runScan`), `git.mjs` (`gitStreamed`, which takes `input` and `delimiter`), `write.mjs` (`STORE_STAGED`), pinned by `test/history.test.mjs`, `test/authors.test.mjs` and `test/write.test.mjs`.
A store is one gzip file, level 1: a line holding the stamp, a line holding the digest of the records, then one record per commit, which is the commit's name, the byte length of its fields, and the `-z` fields git printed for it.
The stamp is one digest, for both walks, over: the store's layout number, the build, git's version, the walk's arguments less its tip, a digest of the effective configuration less the sections `branch`, `remote`, `user`, `credential`, `url` and `http`, the bytes of `.mailmap` and of the files `mailmap.file` and `diff.orderFile` name, the bytes of the shallow file and the grafts file, the object `mailmap.blob` names, the replace refs, and ten `GIT_*` variables (`STAMPED_ENV`).
For the authors walk, which scores a rename on content, it also covers: the index entry and the bytes on disk of every tracked `.gitattributes`, at most 1,024 of them (`HISTORY.mostAttributeFiles`), the root's `.gitattributes` tracked or not, `info/attributes`, the file `core.attributesFile` names or else `$XDG_CONFIG_HOME/git/attributes` or `$HOME/.config/git/attributes`, the file `git var GIT_ATTR_SYSTEM` names, the objects `GIT_ATTR_SOURCE` and `attr.tree` resolve to, and `GIT_ATTR_NOSYSTEM`.
A part that cannot be read is no stamp for the walk that needs it: nothing is replayed, nothing is kept, and the plain walk answers.
A file the stamp reads is a regular file of at most 8 MiB, and one spelled `~user` or `:(optional)`, which is git's to expand, is no stamp.
The order is `git rev-list` with the walk's own arguments, read by the line and used only where every line is a full commit name.
The commits the store lacks are read with `git log --no-walk=unsorted --stdin`, and every commit is replayed in git's order through the reader the plain walk feeds.
A replay stands only where the store and that read account for every commit of the order exactly once; anything else is the full walk.
A store is read only as a regular file git does not track, under any letter case, inside the repository's own `.claude`, at most 64 MiB packed (`READ_MOST`, A113) and 256 MiB inflated (`HISTORY.mostBytes`), at least its two head lines long, whose stamp and digest match and which is records end to end, one per commit.
A link at the name is not followed where the system can refuse one, and a git that will not say whether the store is tracked reads as tracked.
A store is written by `saveHistory` after the map, into the directory the map made, through `atomic`, and only where the walk read a commit the store did not hold.
A write the disk refuses, or one that runs out of memory, leaves no store and is no error; a staged file a killed write left is swept with the store's others (A118).
A dry run reads the stores, writes neither and drops what its walks read.
`isPartialClone` asks one `git config --null --get-regexp` for `extensions.partialClone` and every remote's `promisor` flag, and reads a flag as git reads a boolean (`gitBoolean`): any true value of a remote's flag, or the extension set, is a partial clone.
A git that could not be asked, or a flag git refuses as a boolean, throws, and the scan says the history could not be read (F13).
`runScan` answers with `history`, which says per walk how many commits the store supplied, how many git was asked for and whether the store was written; no plan and no summary carries it
