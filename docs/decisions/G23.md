# G23

Section: G. Scope

## Decision

A release carries the plugin as `npm pack` reads it, `<plugin>-<version>.tgz`, with its SHA-256 and SLSA provenance the release workflow signs through Sigstore with its own identity, written beside the tarball as the Sigstore bundle and as an in-toto provenance file, so `gh attestation verify <tarball> --repo crisnahine/anatomiya` answers which workflow at which commit built it

## Why

A release held the changelog section and nothing else, so nothing a person could download said which commit or which workflow produced the plugin they installed by hand, and the OpenSSF Scorecard read the repository as having no release to check: its Signed-Releases check ignores a release that carries only GitHub's source archives.
The tarball is the shipped set, which `scripts/shipped.mjs` already holds to what the hooks and command files reach, so the asset is what `/plugin install` copies and not a second build; `npm pack` runs with scripts off, as every install here does, and the release job still installs nothing and runs no test.
The provenance comes from GitHub's own attestation action, pinned by commit like every other step, rather than the SLSA generator's reusable workflow, which has to be referenced by tag and would cost the pinned-dependency gate. Its DSSE envelope written out alone is the `.intoto.jsonl` shape the Scorecard and the slsa.dev tooling look for, and the bundle beside it is what `gh attestation verify` and `cosign` read.
`/plugin install` copies the plugin directory from the repository and never downloads the tarball, so the attestation says what the tagged commit shipped and lets a copy taken by hand be held to the tag; it says nothing about the code in it.

## Status
