# E11

Section: E. Baseline and drift

## Decision

The pin follows the remote default branch: the refresh worker pins HEAD when it equals the first of `origin/HEAD`, `origin/main`, `origin/master` that resolves (or, in a clone whose only remote has another name, that remote's `HEAD`), no tracked file is edited or staged, and the current pin is not newer. Never a feature branch, a commit the remote lacks, or a repository with no remote. This narrows E5: the maintainer made the call once, for commits already on the shared default branch, instead of per pin

## Why

Users re-pinned on every branch change, because a pin held on a checkout while the default branch moved read as population-change on every area it touched.
E5's objection is laundering: a re-pin suggested at the moment the agent's own output is largest.
Commits on the remote default branch were merged or pushed to the branch the team shares, so none of them is the work under review, and a clean tree makes the pinned index byte-for-byte that commit (E1, E2).
Measured in `test/refresh.test.mjs`: a feature branch, an unpushed commit on main, an edited file and a local-only repository each leave the pin untouched

HEAD:refs/remotes/origin/main`) are this clone's own work, while a local destination (`git fetch origin main:main`) leaves the tracking ref to the remote's configured mapping and is followed, and `--refmap`, which replaces that mapping, is not, and a session can do any of them, and a commit this clone made itself (any reflog entry names it, except the entries that create no commit: a clone, a checkout, a reset, a branch, a fetch, a push, `remote set-head`, a fast-forward, the empty entry `git worktree add` writes on the new worktree's HEAD (plain `HEAD` read from inside it), and a rebase's `(start)`, `(finish)`, `(abort)`, `(reset)`, `(label)` and `(update-refs)`, each read from the command before the entry's first `: ` and never from a commit's subject, so `feat(reset): ...` is still a commit.
Fail-closed because git names a rebase's steps by whatever ran it, `pull (pick)` with `pull.rebase` set among them, and a list of what creates commits pinned each spelling it missed; a push and `remote set-head` are listed because counting them held the pin for good at a commit the remote had sent) never joins the pin while it sits on the first-parent line from the pin to the tip: `git push <url>` moved no tracking ref before git 2.56, so the ordinary fetch after it brought the clone's own commit back as the team's, and a teammate's commit on top reviews nothing beneath it.
Such a commit is accepted with `anatomiya pin`.
First-parent only, because a branch merged on the remote with a merge commit sits behind its second parent and the merge is its review; counting it stalled the pin for every merge-commit workflow (`test/refresh.test.mjs`).
A commit made on a detached HEAD in a linked worktree is in no shared reflog, and a commit made on the server (the API, a web edit) cannot be told from a colleague's.
Asked through `git reflog` rather than the `logs/` file, which reftable never writes and `core.logAllRefUpdates=false` stops writing: reading that file's absence as a fresh clone followed this clone's own push.
A clone that keeps no reflog is never pinned automatically.
What stays open takes intent rather than accident: a remote reconfigured to point elsewhere, or `git update-ref -m fetch` forging the record; E5's threat is the pin suggested when the agent's output is largest, not a session working to defeat it.
`runPin` takes the commit the refresh judged and refuses if HEAD moved in between.
What each automatic pin accepted (from, to, files in and out) is written to `refresh.json`.
In a fork workflow `origin` is the contributor's fork, and its default branch is what the pin follows; that is said in the README rather than guessed at.
A pin that stops following while the checkout sits on the tip is held, recorded in `refresh.json` (`held`: `made-here` with the commit and what matched it (`by`: `reflog`, or `identity` where only the committer did, which the line says as the commit carrying this clone's git identity rather than being made in this clone), `not-fetched`, `no-record`, `unread`, each with the pin it held) and said when the person starts or resumes a session, not after a compaction or a clear inside one, through `systemMessage`, to the person in the terminal and never into the model's context; a pin moved by hand since the hold ends it at once: the model is the author this row keeps from accepting its own work, and a sentence in its context naming how to accept it is the suggestion E5 refuses.
The line is fixed words and validated commit ids.
The reflog forgets (a removed worktree takes its HEAD's log, a deleted branch its own, and `gc` expires every entry after 90 days), so a commit on the first-parent line whose committer is this clone's own identity (`git var GIT_COMMITTER_IDENT`) is made here too: past a pin, anywhere between the pin and the tip, and on a first pin only from the earliest moment the clone is known to exist, since read over a first pin's whole line, one commit the same person pushed from another machine before the clone existed held every first pin for good.
That moment is the mtime of `.git/description`, which a clone writes once and git never touches again, or the oldest reflog entry where the file is gone; the reflog alone let a commit made here through once `gc` expired every older entry (`test/refresh.test.mjs`).
Past a pin a commit made here is held whatever its date.
A merge or squash made on the remote carries the host's committer and still pins, and a host's fast-forward merge that keeps the author as committer holds, the safe direction.
A walk git cannot answer holds as `unread` rather than reading as a teammate's commit or as one made here.
How the remote's branch last moved holds as `unread` where git could not be asked, since a call with no exit code is neither a push nor a missing reflog, and so does a walk whose committer identity could not be asked for.
With no committer identity at all only the reflog is asked: git makes no commit without one, and holding there held every container that has no git identity.
A pinned commit git no longer holds (a branch squash-merged, deleted and collected) bounds nothing, and the line is read as for a first pin; walked from it, the failure held the pin for good and named no commit.
A pinned commit git could not be asked about, a pin it could not be asked the order of, and HEAD, the remote's tip or a read of the pin itself that could not be asked hold nothing: the worker ends with nothing recorded, and the next refresh asks again (F29).
The fast-forward and rebase-bookkeeping entries are matched as git writes the whole entry, so a commit subject beginning "Fast-forward" or a branch named `wip(start)` is not read as one.
