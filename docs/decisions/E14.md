# E14

Section: E. Baseline and drift

## Decision

A check resolves HEAD once and hands its sha down, the reads that need no other's answer run side by side, and git is asked once per process about commits named by their full sha. The scan resolves the baseline beside the parse

## Why

Measured with 0.13.3 on a clone of this repository with a two-file branch, mapped and pinned at its base: a check made 25 git calls one after another, and 5 were repeats or trivial: HEAD resolved twice, the base ref twice, `merge-base HEAD <sha>` twice, the merge base of a commit with itself, and the same diff twice.
The scan held a parse that needs only the files and the frameworks until the baseline's git reads had answered

## Status

**done** `check.mjs` (`storedOrCollected` collects the corpus once per check however many fields ask it, on the no-map path alone), `git.mjs` (`remembered`, the one helper that holds the full-sha gate and copies a listing out per caller, keeps merge-base, commit resolution, `ls-tree -r` (with its bounds in the key) and the diff of two commits per root and arguments, only where every rev is a full 40 or 64 digit sha, only an answer, so a failure, a throw from a git that could not be asked (F29) and "no common ancestor" are asked again (F15), at most 256 entries, the oldest dropped first and asked of git again when next wanted, which bounds a process handed many commits at the cost of a re-ask; `mergeBase` of a verified commit with itself spawns no merge-base, and asks `merge-base` where that commit could not be asked about; `resolveBaseRef` takes `head` and returns `tip`; `shaReachable` is never answered from memory, since it exists to notice a commit that went away (E3)), `check.mjs` (`resolveBase` returns `head`; the diff, the pending edits, the corpus filter, staleness, the added ranges and the tracked tests are read with `Promise.all`, and each caveat is still pushed where it always was), `baseline.mjs` (`resolve` takes `head`, and its three ranges run side by side), `changeset.mjs` (`changedFiles` and `onlyInHead` take `head`, and the check hands `addedRanges` and `boundary` the same sha), `scan.mjs` (the `resolveState` and `parseFiles` seams).
Pinned by `test/git.test.mjs` (the drop order past 256 included), `test/check.test.mjs` and `test/scan.test.mjs`.
25 calls to 20 on that branch, 17 to 15 with no pin and 20 to 18 with no map, one of them the only read that names HEAD, with byte-identical check JSON on all three; the median check went from 422 to 285ms on the pinned branch, 15 alternating runs at load 4.0 to 4.2, at 70.6 and 70.2 MB.
Scan plans are identical on this repository and five corpus repositories, and peak RSS did not rise on those two: 2,407 and 2,408 MB on a measured React front end, 101 and 85 MB here, 0.13.3 first.
On a measured Rails API it rose 10.2%, for the Ruby threads' heaps (B50).
A ref name is never a key, because tests and agents commit between two calls in one process.
What it gives up: a commit pruned from the object store while a run is going is still answered from memory by everything but `shaReachable`; and `merge-base` is not read as symmetric, so the pin's fork with HEAD and HEAD's with the base are two calls even when the pin is the base, since git does not promise the same answer in both orders where there is more than one merge base
