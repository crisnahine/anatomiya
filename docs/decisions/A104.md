# A104

Section: A. Delivery

## Decision

In `.cursor/rules` and `.github/instructions` every path component is a directory of the repository's own, or is not there yet. A target is in one of three states, `on`, `off` or `unknown`, and an unknown one is neither written nor cleared

## Why

A link at any of those components is refused wherever it leads, and so is a directory that is, holds or sits inside the place `.claude/rules` resolves to.
F2 lets `.claude/rules` alone lead elsewhere in the tree, because one measured repository shares that directory through a link.
These two directories get no such exception.
`.github` holds workflows, so a link there that resolves inside the tree is still a place a map must not land.
And a `.claude/rules -> ../.github/instructions` link makes two targets one directory, where Claude Code would load the other reader's files as its own.
The overlap is compared on native real paths: measured, the plain form keeps the link's own spelling on a volume that folds case and misses `../.GitHub/instructions`.
`off` is what removes a map, so it is said only where it was seen: nothing at the overview's name, or a file there that is not this tool's.
Everything else is `unknown`: a link or a non-directory on the path, a path or an overview that will not open, an overview that is a link or not a file, and the overlap.
Were a mode-000 overview read as off, a refresh nobody watches would plan the removal of every file there.
The directory is asked for again wherever a swap would matter: when the plan is made, before anything is created, after every temporary file is staged, before each rename, before each removal and before each put back, and a component this run creates is looked at again after its `mkdir`.
Measured on an existing map: 42 of 42 injected failures put every file back, and 118 kills in the middle of a write lost no file a person wrote

In a Cursor or Copilot directory the scan did not name, the lock stops that directory alone, since a permission in a directory another tool owns may not stop Claude Code's map (`spared` and `settle` in `commitMap`): the record is written again with the names that directory had on record, then what was replaced there is put back and its staged files are removed, the other directories are written, the target reads `unknown` and `unwritable`, a refresh comes due again on its retry clock while it does (A95), and the scan exits 0 saying `.cursor/rules could not be written (.cursor/rules/anatomiya-overview.mdc could not be replaced (EPERM)), so nothing there was written or removed: close what holds it or change its mode, then scan again`.
A directory that refuses a new temporary file on one of the same three codes is ruled the same way one step sooner (`stage`), which is the path a read-only directory takes where `fs.access` reads no ACL: not named, its staged files are removed, nothing there is renamed or removed, the record names what it held and the scan says `.cursor/rules could not be written (a file could not be created in .cursor/rules (EACCES)), so nothing there was written or removed: fix its permissions, then scan again`; named, or in `.claude/rules` or `.claude/anatomiya`, the scan refuses before any rename with `a file could not be created in .claude/rules (EACCES), so nothing was written: fix its permissions and scan again`, where the raw error would print the temporary file's absolute path.
A put-back that fails there, a second record write that fails, or an error that is no lock refuses the whole scan.
Given up there: a dry run renames nothing and says `would write`; and a leftover removed from that directory before the lock was met stays removed.
The second record write comes before the put-back and not after the last removal: measured with a process killed between the put-back and a record write placed after it, the record named a file that was not on disk and missed one that was, and every later plain scan counted that file as an entry left there until `scan --targets claude` removed it.
With the record first, a process killed during the put-back or at the first rename after it leaves a record that names exactly the map files the directory holds, and the next scan writes the directory, removes the stale file and counts nothing left.
Killed before that write, the record renamed first names the files each directory had left to remove, and the next plain scan removes them (A13); the second write keeps the stopped directory's list as the record on disk had it.
What is left open: the last look and the rename or unlink after it are two calls, so a directory swapped for a link between them is written or removed through once, and closing that takes a directory handle the calls used here do not carry.
Temporary files staged through such a link can stay, after a refusal as after a kill, since the unlink goes through the link and misses.
The next scan that writes or removes in that directory, or leaves the target out by name, removes each regular file named as a map file plus `.tmp-<pid>-<16 hex>` whose stager is not running (`stagedBy`), and a run that read no file of any language, which writes nothing, removes none.
