# A116

Section: A. Delivery

## Decision

Claude Code's transcript records are read in one module, `transcript.mjs`, by functions that take text, so a hook that needs several answers off one transcript reads it once for each moment it needs them. The end-of-turn check reads the head once and the tail at most twice: before its git reads, for the turn's start and the session's tool calls, and after them, where a change is pending, for what the session already asked

## Why

Each reader opened the transcript for itself and read up to 64 MiB of its tail, so a stop that ran all four readers made one head read and four tail reads.
One tail read cannot serve all four: the git reads between them take seconds, and an ask another stop writes in that time has to be seen, or the same change is asked about twice.
So the tail is read again after the git reads, and the first copy is let go before them, so two 64 MiB strings are never held at once.
The cost is that second read: up to `TRANSCRIPT_MOST`, 64 MiB, of the tail read again on a stop with a change pending.
Measured in process on two of this machine's transcripts, the transcript reads alone with no git, five alternating runs each at a load average near 10, medians: 204.2 ms to 151.2 ms on 33,226,402 bytes, and 170.4 ms to 121.4 ms on 27,370,144 bytes, with the same answers.
A compaction is read by two predicates that stay apart: the echo ends its window at the system record alone (A92), and the delivery measurement counts the boundary or the summary after it as one event (A17)
