# B8

Section: B. Engine

## Decision

A checker that resolves under 0.80 of its type lookups, or whose config was refused, reads `degraded`, prints no count for its claims, and is not run again by a refresh while nothing in its stamp has moved. A failed run (`tier-failed`) is followed by one more run on the next refresh, and from the second in a row under one stamp it is carried the same way. A root `tsconfig.base.json` is read where there is no `tsconfig.json`, and no root is skipped for what its config holds or lacks

## Why

Measured: typed resolution drops 89.5% to 39.8% silently.
Asked again of a root with no `tsconfig.json`, on thirteen repositories with their dependencies installed (`docs/measurements/2026-10-07-checker-root-config.md` holds every table this row draws on): reading a root `tsconfig.base.json` moves three of eight over the 0.80 floor (nxext/nx-extensions, angular-ngrx-nx-realworld, analogjs/analog), two were over it on the compiler's defaults, and three stay under it (angular-challenges, eslint, prisma); of five roots with neither file, one resolves on the defaults.
Whether each of the eight bases declares `paths`, read 2026-10-08 from the repository's default branch: nx-dotnet 10 entries, devkit 7, nx-extensions 10, analog 28, angular-ngrx-nx-realworld 20, angular-challenges 23, eslint none, prisma none.
No skip on a base config without `paths`.
Among the first eight base-only roots measured, the six that declare `paths` include the five that resolve and the two that declare none both degrade, which is the split the question asked about.
Fourteen more roots whose base declares no `paths` were then measured with dependencies installed (`docs/measurements/2026-10-08-base-config-without-paths.md`): six degrade, seven resolve over the floor and one reads ok with no rate.
So of sixteen such roots eight degrade and eight do not, and a skip would close the eight that answer.
Nothing recorded separates the two halves: workspace kind, package manager, whether the base extends something, configs below the root and the share of TypeScript all overlap.
Four more roots that declare `paths` read ok, nine of ten in all.
The carried verdict already takes the cost off every refresh.
Given up: such a root pays the checker once per scan a person runs, 3.2s on eslint and 11.4s on prisma, the median of three scans with the checker less the median of three without (4.2s less 1.0s, 13.5s less 2.0s).
No static fact separates the two groups compared on the corpus either, the four repositories that degrade and three that read ok through a root `tsconfig.json`, so nothing is skipped there.
A repository whose checker degrades pays for it once per scan a person runs and not on a refresh that carries the verdict: 4.4s to 21.2s with the checker against 1.2s to 3.8s with the verdict carried, on eslint, react, prisma and Ghost

## Status

**done** `tsconfig.mjs`, `semantic.mjs` (`classifySemantic`, `RESOLUTION_FLOOR`), `reduce.mjs` (gate `degraded-semantic`), `render.mjs`.
Three causes kept apart: a config that could not be read keeps its own reason; a config that read cleanly while resolution fell under 0.80 reports `low-resolution`; and a root with no tsconfig.json is not degraded by rule.
One with a `tsconfig.base.json` instead is read through that (`CONFIG_NAMES`, `configNameIn`), under the containment a root config gets, and is judged like any config that read: `low-resolution` under the floor.
Plain JavaScript with neither is not checked at all (B7, `plain-javascript`); anything else with neither runs on the compiler's defaults, is judged by the rate like a clean config, and names `no-tsconfig` only when the rate falls under the floor.
No skip on a missing config, measured 2026-10-07 on thirteen repositories with their dependencies installed.
Eight keep a base and no root config: read on defaults, two resolved over the floor (nx-dotnet 89.6%, jscutlery/devkit 83.6%) and six did not; read through the base, five do (nx-dotnet 97.6%, devkit 84.9%, nxext/nx-extensions 79.9% to 84.9%, angular-ngrx-nx-realworld 68.9% to 91.7%, analogjs/analog 76.7% to 85.5%) and three do not (angular-challenges 71.1%, eslint 60.9%, prisma 65.9%).
Five keep neither: cloudflare/workers-sdk resolved 82.9% on defaults, react, Ghost and immich read 60.2%, 54.9% and 34.2%, and formbricks ended `tier-failed` when the checker's child aborted after 3,370 of 4,099 files.
So three roots with no `tsconfig.json` answer today and a skip on the missing file would close them; what a degraded run costs is the checker's own time, which the refresh table in this row gives for eslint, react, prisma and Ghost.
A background refresh does not pay that again where the answer is already known: when the record's tier reads degraded, was measured by a run that finished or by two failed runs in a row under that stamp (`semantic.failures` 2, `FAILURES_CARRIED`), and `verdictStamp` (this build's version, `checkerStamp`, the size and modification time of `node_modules` and of each install record in it, and the bytes of the config the root is read through) equals the stamp it was measured under, the refresh scans with the checker not run and records the same status, reason and rate with `carried: true` beside `measuredAt` and `measuredUnder` (`carriedVerdict` and `verdictStamp` in `semantic.mjs`, `passes` in `refresh-run.mjs`, `scan` in `scan.mjs`).
A carried verdict is carried again.
The record is an untracked file anyone on the machine can write, and a carried verdict is printed in the always-loaded overview on every refresh after, so `carriedVerdict` hands a scan only what a scan could have written: status `degraded`; `ran` or `carried` true; a reason from the config reader's refusals (`CONFIG_REFUSALS` in `tsconfig.mjs`: `config-escaped`, `reference-escaped`, `unparseable`, `extends-escaped`, `config-errors`) with a rate that is null or from 0 to 1, or `low-resolution` or `no-tsconfig` with a rate from 0 up to and not at the 0.80 floor, which is what `classifySemantic` answers, or `tier-failed` with a null rate and a `failures` of 1 or 2, a count other than 0 or none beside any other reason being measured; and a `measuredAt` that is the ISO string of a moment from 2020 on and at most a day after now.
It copies those five fields and `failures`, and no other key.
Any other record answers null and the refresh measures: of 33 records edited by hand with the stamp left matching (a reason holding new lines and a heading, a reason that is a number, an object or null, a rate of `"abc"`, 5, -1, 0.99, `1e999`, true or an object, a `measuredAt` in 2099, of free text, empty or a number, a stamp absent, null or an object, a tier that is a string or an array, a `failures` of 2 beside a run that finished), 29 are measured and print the measured sentence, and four carry: the record untouched, one whose reason is rewritten to another reason of the list, one with a key no scan writes, which is dropped, and one with no `failures`, which is how every degraded record written before the count reads.
Of 17 failed records edited the same way, the untouched one hands on its 2 and is carried, one rewritten to 1 hands on 1 and the checker runs, and the other 15 are measured with nothing behind them (a count of 0, 3, -1, 1.5, a string, none; a rate beside the failure; a stamp absent).
A config that refused degrades the tier at any rate, so its rate is not held under the floor.
The stamp reads the root config the way the checker's reader does: one that leaves the repository through a link contributes `config-escaped` and is not opened, and one that is not a regular file contributes its kind.
A scan run by hand always measures, with or without `--dry-run`, and so does a refresh once the stamp moves, the build changes, or the record holds no stamp, which is every record 0.13.4 wrote; `pin` runs no checker.
An ok tier is never carried: it is measured on every refresh, since its numbers are the claims.
A failed run measured nothing, and one can be a machine under load, so carried on its first sighting it would stick: the first is handed to the rescan with its count, the checker runs, and the second under one stamp is carried (`standsIn`, `failuresIn`).
A run that finishes records 0, and a failed run under another stamp, or in a scan run by hand, is the first again.
Run by hand on a fixture of 1,500 generated TypeScript files, the checker's child made to abort by a 200 MB heap limit: a scan by hand recorded `tier-failed` with `failures` 1; a refresh after an empty commit, under the limit, ran the checker and recorded 2; a refresh after another, with no limit, ran no checker and recorded `ran: false`, `carried: true` and 2, its overview saying `type-checked claims are not counted: no type lookups resolved when measured 2026-10-08 UTC (tier-failed)`; and a scan by hand with no limit read ok with `failures` 0.
`test/refresh.test.mjs` holds the same four steps around a checker whose worker cannot start.
Given up: a failure that load causes on two refreshes in a row sticks until the stamp moves or a scan is run by hand, and a repository whose checker always fails pays for two runs per stamp and one per scan by hand.
No option switches this (A24), and the schema stays 19, since 0.13.4 never reads the record's `semantic`: given a record holding `failures` 2 and `carried`, its `check` and its `scan` both ended with exit 0.
The premise, measured 2026-10-08 on four installed clones at HEAD and 50 commits back on the same `node_modules`: eslint 60.9% and 60.9% (19 days of commits), prisma 65.9% and 65.6% (6 days), react 60.2% and 60.3% (25 days), Ghost 54.9% and 54.7% (15 hours), each with the same reason at both commits, so none crossed the floor.
A refresh after an empty commit, wall time and peak resident memory, median of three, with the checker run against the verdict carried: eslint 4.4s and 808 MB against 1.2s and 160 MB, react 8.9s and 1,421 MB against 2.8s and 208 MB, prisma 13.9s and 2,132 MB against 2.3s and 211 MB, Ghost 21.2s and 2,681 MB against 3.8s and 243 MB.
The install records are `.package-lock.json` (npm), `.modules.yaml` (pnpm), `.yarn-state.yml` (yarn 2 and later with the node-modules linker) and `.yarn-integrity` (yarn 1), each seen in an install on the corpus clones: eslint and huginn hold the first, Ghost, prisma and typeorm the second, mastodon the third, react, webpack, whitehall and diaspora the fourth.
They are read with a stat of the entry itself, and a `node_modules` that is a link is no install and stamps nothing, as for `hasInstall`.
Without them a verdict measured over a partial install is carried past the install that completes it: a fixture importing two packages that are not installed reads degraded at 0%, and once both are written into `node_modules` the refresh measures and reads ok at 100%.
An install starts no refresh by itself: the stamp that starts one (`stampOf` in `refresh-run.mjs`) holds `checkerStamp`, which reads whether `node_modules` holds a package, and not the install records.
So the verdict is measured by the next refresh that a commit, a checkout or a pull starts, or by a scan run by hand.
Measured on a fixture: a scan, a commit and a refresh that carried; the missing package installed and `.package-lock.json` rewritten, and a refresh ran nothing, the overview still reading `0% of type lookups resolved when measured`; an empty commit, and the refresh measured and read ok at 100%.
Given up: a repository whose code changes lift it over the floor stays degraded until someone runs `scan`; an edit to a config the root config extends or references does not end a carried verdict, since the stamp holds the root config's own bytes: not a config it extends, and not the one it names first under `references`, which is the config read where the root builds nothing; an install into a nested `node_modules` alone, or by a package manager that keeps none of the four records and adds no entry to the root one, moves no stamp; a tool that creates or removes its cache directory in `node_modules` costs one measured refresh; and with none of the four install records present, a package's file rewritten in place or a scoped package added under an existing `@scope` moves no stamp.
Whether bun leaves a record was not verified, since bun is not installed where this was measured.
