# B48

Section: B. Engine

## Decision

A scan's independent stages run side by side, and nothing it does between files holds the parent: the type checker and the history read start beside the parse, a Ruby corpus of 1,000 files or more is read by several children whose answers are joined in input order (up to four over byte-balanced batches, B50), the compiler host answers each path's containment once per build, and the memory guard's `ps` is asynchronous

## Why

Measured on the 35-repository corpus, every map byte-identical before and after, the whole corpus took 429s before and 262s after (mastodon 16.8s to 7.3s, empire-flippers api 10.1s to 5.9s and client 26.6s to 20.5s): the checker and the history read waited for a parse they never read; one Ruby child left the parent idle for most of discourse, 22.1s with one child, 13.5s with four, 12.8s with six; re-walking `realpath` from the root on every ask was 45% of building ef-client's program (10.8s to 5.8s), and the host takes the tree as fixed for one build, so a scan with the checker measured about 7x a plain one on empire-flippers client in 0.13.3 (1.9s against 12.6s, down from 2.2s against 17.4s in B7) and about 4x on typeorm (1.8s against 6.8s), and about 10x and 5x in this build, since B49 and B50 made the plain scan faster (client 1.3s against 12.2s, typeorm 1.3s against 5.8s, medians of three with the checker switched off in the scan for the plain one); a synchronous `ps` every 25ms held the parent 1.7s of a 20,000-file scan.
The Ruby walk keeps the enclosing def and class as it descends, as B47 does for the JS walk.
The cost is peak memory: the checker (880 MB measured) now sits beside the parse workers instead of after them, so it waits for the parse where the pool has one worker, and a scan that fails mid-parse stops it rather than waiting on it.
A Ruby child that dies charges the rest of its own batch, not the rest of the corpus
