# B48

Section: B. Engine

## Decision

A scan's independent stages run side by side, and nothing it does between files holds the parent: the type checker and the history read start beside the parse, a Ruby corpus of 200 files or more is read by several children whose answers are joined in input order (one per 100 files, up to four over byte-balanced batches, B50), the compiler host answers each path's containment once per build, and the memory guard's `ps` is asynchronous

## Why

Measured on the 35-repository corpus, every map byte-identical before and after, the whole corpus took 429s before and 262s after (mastodon 16.8s to 7.3s, a measured Rails API 10.1s to 5.9s and the front end 26.6s to 20.5s): the checker and the history read waited for a parse they never read; one Ruby child left the parent idle for most of discourse, 22.1s with one child, 13.5s with four, 12.8s with six; re-walking `realpath` from the root on every ask was 45% of building the front end's program (10.8s to 5.8s), and the host takes the tree as fixed for one build, so a scan with the checker measured about 7x a plain one on a measured React front end in 0.13.3 (1.9s against 12.6s, down from 2.2s against 17.4s in B7) and about 4x on typeorm (1.8s against 6.8s), and about 10x and 5x in this build, since B49 and B50 made the plain scan faster (the front end 1.3s against 12.2s, typeorm 1.3s against 5.8s, medians of three with the checker switched off in the scan for the plain one); a synchronous `ps` every 25ms held the parent 1.7s of a 20,000-file scan.
The Ruby walk keeps the enclosing def and class as it descends, as B47 does for the JS walk.
The cost is peak memory: the checker (880 MB measured) now sits beside the parse workers instead of after them, so it waits for the parse where the pool has one worker, and a scan that fails mid-parse stops it rather than waiting on it.
A Ruby child that dies charges the rest of its own batch, not the rest of the corpus

## Status

**done** `scan.mjs`, `ruby.mjs` (`parseBatch`, `shardsFor`), `tsconfig.mjs` (`perBuild`), `contained.mjs` (`resolveInside` takes `realpath`), `pool.mjs` (`rssOf` is async and never rejects; a kill is checked against the job it was read for), `semantic.mjs` (`runSemantic` takes `signal`, and `stopWhen`, B72), `ruby-walk.mjs`.
The scan discovers its areas before it waits for the checker, so the checker's reader folds them while the checker still walks (B72).
Merged children report `stalled` only when none of them answered a version, as one child would
The shard floor came down from 500 files to 100 on 2026-10-29: the 500 kept every corpus under 1,000 Ruby files on one child, and on a 929-file Ruby repository one child read them in 5.8 to 5.9 s where four read them in 2.0 s, byte for byte the same plan, result and index, at a process-tree peak of 370 MB against 200 to 236 MB, which is under what the same four shards already cost on a larger corpus.
Running the three engines' batches side by side was measured the same day and refused: on mastodon, 3,258 Ruby files beside 710 of TypeScript, the scan went from 2.1 to 2.4 s to 2.05 s and the process-tree peak from 730 to 754 MB to 930 MB, the oxc pool and the prism shards alive at once, and on bitwarden the time did not move; B50 refused six shards for a 4% to 16% gain at 22% to 30% more peak, and 3% for 27% is the same bar.
