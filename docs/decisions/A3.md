Section: A. Delivery

## Decision

Ownership = filename prefix AND `generator: anatomiya` frontmatter AND named by `facts.json`, as a file the map holds or one the scan that wrote it was about to remove. All three, or leave it alone

## Why

v3 said "never delete a file lacking the key" and "remove any unknown `anatomiya-*`" in adjacent sentences

## Status

**done** `rules.mjs` (`auditRules`, `knownNames`, `pendingNames`, `pendingAmong`, `isOwned`, and `readHead` exported for the read side), `write.mjs`, `hook.mjs` (`ownMap`, `readOwned`).
The third fact was the one nobody read: the writer removed on prefix plus key plus absence from this scan, which deletes an older build's output and anything a store wiped between runs.
The map is read before the new one replaces it, and no map at all makes nothing removable rather than everything.
A file carrying two of the three is reported and left where it is.
The rule is about removal: a hand-written file that took a name this scan writes is replaced, because a generated name is this tool's by construction and refusing the whole map over one would let a repository stop the map being built at all.
That is the only case, it is reported on the summary, and the overview does not then call it a file this tool did not write.
The rule reaches the read side too, arriving late and from a report: the hook echoed whatever sat at the overview's path, so a file this tool never wrote went into the model's context on every prompt and every tool call, and the only reason it had not bitten anybody is that the path is a name nobody else types.
It asks the frontmatter now, which is the one of the three facts a hook can check: the prefix is the path it just built, and `facts.json` belongs to a scan rather than to a session.
So the read side is two of three by construction, and the gap is worth stating rather than hiding, since a file carrying our key is a file anyone can write.
Whose it is also decides whether the walk stops: a hand-written file in a subdirectory used to silence the repository's own map for every session under it, and the walk now goes past it to the real one above.
Second-order, and the reason the read goes through `readHead` rather than a plain read: the path is whatever is sitting there, and this runs on every tool call.
A named pipe there never returned at all, which is a session that never returns, measured; a five-megabyte file carrying our key was read whole and echoed whole, 100 MB resident and every byte of it into the context window.
`readHead` opens non-blocking, types the shape before reading a byte, and stops at `HEAD_BYTES`, the size this repository had already decided a rule file may be.
The frontmatter test itself was reading across the closing fence, so somebody else's block with our key further down came back as ours, which is the direction that deletes; the lines between the fences are now any line that is not itself a fence.
That test was a regex whose lazy line group re-tried every line after every candidate key, so it was quadratic in the shape a repository can ship: a file opening with `---` and repeating `generator: anatomiya` with no closing fence took 24 s at 32,000 lines, a 1 MB overview of it held the echo hook for 50,621 ms against its 5 s timeout, and three such files took a scan to 152 s.
`isOwned` reads the frontmatter by hand now, one line at a time up to `HEAD_BYTES`, BOM and CRLF as before, and answers the same cases (`test/rules.test.mjs`).
The record's second list, `removing` per target, is what the third fact also reads: a scan writes it into the record it renames first, before its first rename, and writes the record again without it once its removals land (A13); `pendingNames` reads it back, keeping only map names, and an older record reads as an empty list.
`check` and `doctor` read the same list.
`check` still lists such a file among those the map does not name, since it loads, and says under that list that the next scan removes it, with `removing` beside `unknown` in `--format json` only where it holds a name; `doctor` counts it on a line of its own rather than among the entries a scan neither writes nor removes (A102)
