# A92

Section: A. Delivery

## Decision

The echo delivers the map once per 192 KiB of what the model reads, about 30k tokens: it stays silent while the last 192 KiB of transcript records the model reads hold a delivery of the same map with no compaction after it, the calls of one parallel batch deliver one copy between them, and a subagent or workflow stage is answered from its own transcript

## Why

A24 re-delivered on every turn and every tool call, and Claude Code does not dedupe hook context: four byte-identical copies in one session all reached the model (`docs/research/what-a-repeated-hook-context-costs.md`).
Counted by `scripts/measure-echo.mjs` over 3,502 local transcripts, main and subagent, on 2026-09-23: 61,996 of 65,977 deliveries (94.0%) repeated the one before with no compaction between, and replaying this rule keeps 7,857 of them (11.9%).
The recency A24 was for is kept by distance rather than by count: a copy further back than the window is delivered again.
The same script reads transcript bytes per context token off the assistant's usage: a median 9.0 and a p10 of 6.4 over 219 sessions, so 256 KiB of every record was about 29k tokens of context at the median and 41k at the p10.
Counted over every record, one 78,191-byte `prompt_snapshot`, which the build writes for itself and never hands the model, put a delivery past the 256 KiB window within one tool call on 2.1.296: 301,845 bytes on, 223,654 without it.
So the window counts only what the model reads: `user` and `assistant` records and the attachments carrying `rendered`, which the 2.1.296 bundle sets only on an attachment that converts into messages, less `instructions`, the CLAUDE.md files, which one session's context held ahead of the delivery they follow in the transcript, seen there and not traced in the bundle (`docs/research/what-a-2-1-296-transcript-holds.md`).
Measured in that unit over 34 sessions on 2.1.292 to 2.1.296 (2026-10-11): a median 6.57 bytes per token and a p10 of 5.69, so the window is 192 KiB, about 29.9k tokens at the median and 34.6k at the p10, keeping the distance in tokens (`docs/measurements/2026-10-11-echo-window-in-conversation-bytes.md`).
The hook reads back at most 1 MiB to find those 192 KiB and delivers past it, as it did before this row.
Replayed through the hook's own walk over 3,848 local transcripts on 2026-10-12, the rule keeps 8,063 of 32,591 deliveries; the forward replay it was first counted with kept 8,581 there, and 9,267 of 46,370 over the 4,328 transcripts the machine held on 2026-10-11 (A119).
A changed map carries a new `digest` of its body and is delivered on the next call, so a re-scan still reaches a running session; a rewrite that touches only the frontmatter is the same map.
Live on 2.1.280 with the same task: 9 deliveries in the main window and 2 in the subagent before, 2 and 1 after, the second main one past the window by design.
Only a real delivery counts: `echoEvent` parses each line and takes only a `hook_additional_context` attachment, so a tool result quoting the map is not one, while a `compact_boundary` entry ends the search.
Anything unreadable, a missing transcript, a directory, a malformed `agent_id`, answers "deliver", which is the behaviour before this row.
One gap is named rather than closed: another plugin's hook context that quotes this map verbatim reads as a delivery, since the attachment carries no field naming the hook that wrote it.
A subagent's calls carry the session's `transcript_path` and their own `agent_id`; its window is logged at `<session>/subagents/agent-<agent_id>.jsonl`, or for a workflow stage at `<session>/subagents/workflows/<run>/agent-<agent_id>.jsonl`, where 9,360 of the 11,328 subagent logs on this machine sit.
The runs are listed at most 256 deep, against 20 in the busiest session measured.
A missing or null `agent_id` is the main thread.
Parallel calls in one batch run their hooks before any of their records is written, so none sees the others' deliveries: re-measured 2026-09-30 on 2.1.285, a session started one directory up got four copies from five parallel reads into a checkout.
So the calls share a batch claim, `${CLAUDE_PLUGIN_DATA}/echo/<16 hex of the transcript path>-<the map's digest>`, holding the transcript offset its maker read up to, and a sibling reads it as a delivery made at that offset, through the same window rule.
The decision is taken under `<batch claim>.lock`, made with an exclusive create, and a call that finds the lock taken stays silent; under the lock the batch claim is read again, and one past the caller's snapshot is judged against the transcript as it is then, stale only past the transcript's size.
A batch claim is replaced by writing `<batch claim>.<pid>` and renaming it, so no reader sees it half written.
A lock whose mtime is more than 7 s from the clock, either way, was left by a call that died holding it: the echo's 5 s hook timeout, plus 2 s, since FAT keeps an mtime to 2 s.
No call breaks a lock nearer the clock than that: the right to remove one dead lock goes to the call whose exclusive create of the lock token `<batch claim>.lock.<its mtime in ms>` wins, which removes the lock only while its inode and mtime, read exactly since an NTFS file id runs past what a float holds, are still the ones it found dead and then removes the lock token; every call then goes to the one create of the lock, and the losers stay silent.
A lock token whose mtime is more than 62 s from the clock was left by a call killed while it broke the lock, and is a dead lock itself: it is broken the same way under `<lock token>.<its mtime in ms>`, one level down and no further (A117).
A lock token the system refuses to remove is left for the sweep, and a dead lock it refuses to remove makes the call answer alone; an exclusive create Windows refuses with EPERM, its answer for a name another process is still deleting, is tried again seven times, after waits doubling from 1 ms to 64 ms, before the call answers alone.
An empty directory at the lock's name is removed and that call takes the lock, and a directory holding entries there is left whole, so each call answers from the transcript alone.
Moving a dead lock aside instead freed the name for a third call while the first holder still held it: at 3 calls over a dead lock, 5 to 40 of 100 rounds delivered twice and up to 36 locks were left with no holder.
Batch claims, locks, lock tokens and a token's own token older than a day are swept on each new batch claim, reading at most 4,096 names.
Measured with 3 and 8 echo processes started at once, 20 rounds each, with no batch claim and with a stale one: every round delivers one copy, where the same test on the build before the lock gave 2 and 3; and 50 rounds each over a dead lock deliver one copy and leave no lock and no lock token.
On the Windows runners every round of those tests that delivered twice, 6 over three runs of each leg, had an exclusive create answered EPERM while another call deleted that name, and with the create tried again none did; each of the 12 creates refused was taken on the first retry (`docs/measurements/2026-10-12-windows-echo-eperm.md`).
Where the plugin names no data directory, or it cannot be written, each call answers from the transcript alone, one copy per call at worst.
What this gives up: a call killed while it holds a lock token leaves that dead lock in place, so the echo for that window and map stays silent for the 62 s until the lock token reads as dead and the next call breaks both; a call killed while it holds a token's own token leaves them in place until a batch claim another window or map makes there a day or more later sweeps all three; a dead lock the system will not remove makes each call that reaches it answer alone, at most one copy per call, until it can be removed; and after the clock is set back, a lock token the system would not remove can carry the name of a later dead lock, whose window stays silent while that lock token reads as live and whose calls each answer alone after that, until it can be removed or the sweep takes it; and a call suspended past 7 s while it holds the lock, a laptop asleep in those milliseconds, is taken for dead: the next call breaks its lock and decides beside it, and its release later removes whichever lock is there, so that batch can deliver a copy or two more.
A workflow stage's transcript carries no `toolUseResult` copy of a tool's output and runs about 4.3 bytes per token (136 logs, median 4.28, measured 2026-10-23), so there the 192 KiB window is about 46k tokens, against about 29.9k in a main thread or a plain subagent's, whose logs carry the copy.
