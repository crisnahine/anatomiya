# B58

Section: B. Engine

## Decision

`$lib/x` is read as SvelteKit's alias for the importer's own `src/lib/x`: tried as `<ancestor>/src/lib/x` for each directory above the importer, read where one file answers, and never matched as a path tail

## Why

shadcn-svelte writes 4,213 `$lib/` imports against 2,199 relative ones, and none of them resolved, so "most imported from here" ranked what was left.
Read as one more root prefix and matched on the path tail, 2,683 resolved and 1,530 did not, nearly all because a second `src/lib` tree holds the same tail, and a tail two files answer resolves to neither.
Those were the most imported files in the repository, `$lib/utils.js` with 458 importing files among them, and probes of the same rule resolved into a sibling application's `src/lib`, into a `tools/lib`, and into a `lib` nested under the right one.
Anchored on the importer, 4,210 of 4,213 resolve, none outside the importer's own project, with all 2,683 answers of the tail match unchanged; the 3 left name two paths the importer's `src/lib` does not hold and one asset.
Fifteen resolutions drawn with a fixed seed were opened, and each is the file under the importer's own `src/lib`.
The `docs/src/lib` area's line went from `useDesignSystem (22 files), UseClipboard (15)` to `cn (447 files), WithElementRef (157)`. kit's map files and `facts.json` are the same under both rules.
A root prefix (`@/`, `~/`, `#/`, `src/`) written in a `.vue` or `.svelte` file is anchored the same way: tried as `<ancestor>/x` and `<ancestor>/src/x` for each directory above the component and never matched as a path tail, so where no ancestor holds the file the import credits nothing.
Where two directories above the importer answer with different files it credits nothing either, the answer the tail match gives two candidates: `src/features/cart/CartPage.vue` importing `@/components/Button.vue`, with a `src/features/cart/components/Button.vue` and a `src/components/Button.vue` both present, names neither, since the alias means one root and the nearest directory is the feature's own folder as readily as the project's.
One file reached from two directories, `src/components/x` as `components/x` under `src` and as `src/components/x` under the root, is one answer.
Asked of every alias import a pattern over the import lines finds in supabase, shadcn-svelte, kit, element-plus, vitepress and storybook, 4,238 of them in shadcn-svelte and 108 in supabase, none resolves differently with that rule than with the nearest directory taken, and supabase's line still reads `Button (37 files), Card (30)`.
A component answers no bare tail, so the tail match handed a component's import of its own package's `Button.vue`, written `@/components/ui/button`, to the one file left that fits, a React `button.tsx` in another package: supabase's `apps/ui-library/registry/default/components/ui` (25 `.tsx` files) read `Button (48 files), Card (42)`, 11 and 12 of them `.vue` files under `blocks/vue`, and reads `Button (37 files), Card (30)` anchored, as it does in 0.13.4.
Measured on supabase, storybook, cal.diy and next.js: 64 imports resolve differently, all in supabase.
41 name nothing where they named a `.tsx` file of `apps/ui-library` (card 12, button 11, label 8, input 8, cursor 2), and 23 that the tail match left ambiguous name a file of the Vue package (10 name `blocks/vue/registry/default/lib/utils.ts`), which takes `blocks/vue/registry/default` from `cn (9 files)` to `cn (17 files)`.
Two map files change and none in the other three.
The same anchor for every importer was measured and refused: for the importers that are modules it resolved 1,408 imports the tail match leaves ambiguous across the four and dropped 159 it resolves, and the nine dropped ones opened were right. cal.diy points `~/*` at `apps/web/modules/*`, a directory beside its importers under `apps/web/app` and above none of them, so `Shell` went from 14 importing files to 4 and the `apps/web/modules/apps` line was lost; supabase's `@/data/api` is an `api.d.ts`, which no path candidate spells.
Against 0.13.4 on the four, two roster lines differ, both in supabase areas of the Vue package that 0.13.4 printed no line for, since it read no `.vue` importer

## Status

**done** `siblings.mjs` (`LIB_ALIAS`, `ALIASES`, `specifierToFile`, `inProject`, `fileAt`), pinned by `test/siblings.test.mjs`.
A path's trailing slashes are stripped by a walk from its end (`withoutTrailingSlashes`), at each of the three places one is cut: a pattern anchored at the end tried every start in a run of slashes, and in release 0.13.4 one specifier holding a run of 20,000 took 250 ms and one of 80,000 took 4,250 ms, where each takes under 1 ms here.
The alias lookup reads an index of every path tail and the directories it sits under (`projectIndex`), holding a tail's one directory as the string itself and a Set from the second: on 100,000 files eight segments deep it retains 74 MB where a Set for every tail took 195 MB, and 18 MB against 49 MB on 25,000.
What this gives up: no `svelte.config.js` is read, so a project that repoints the alias resolves nothing through it; a bare `$lib` with no slash is not resolved, and neither repository writes one; `$lib/../x` leaves `src/lib` through the `..`, as the bundler does; SvelteKit's virtual modules (`$app/`, `$env/`) name no file; no `tsconfig.json`, `vite.config` or `nuxt.config` is read, so a component whose alias is rooted beside it and above none of its directories credits nothing; a component whose feature folder and whose project root both hold the file its alias names credits neither, which gives up a true credit as well as a wrong one: a package's own `src/utils/fmt.ts` is credited to nothing where the workspace root holds the same path, and the same through `$lib` where a root `src/lib` holds the name (7 of 20 probe cases went from a file to no credit, and 0 imports changed on the six measured repositories); and a module's alias import is still matched as a tail, so a module can be credited to another package's file where one tail fits
