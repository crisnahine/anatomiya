# G20

Section: G. Scope

## Decision

The docs gate reads each document once, through `documents(root)`, and runs its claims as a table of rules, `RULES`, each a function of one context, so a rule can be run on its own over documents held as strings (`documentsFrom`) and a rule added shows by name

## Why

`checkDocs` was one 563-line body whose 27 read sites went through an uncached `readFileSync`: measured, 2,885 reads of 985 files per run, 825 of them read more than once, the README fourteen times and every row file twice.
The same run reads 990 now, the five past one per file being the release-notes reader's own; it takes the same 1.5 s either way, since the reads were never its cost: the two spawns of the binary and parsing the sources are.
A rule could be reached only by running all 16, so 71 of the gate's 133 tests copied the plugin, the documents, the scripts and the tests into a temporary tree and spawned the gate, 28 MB per case.
The body is now a reading, `documents(root)`, a context of what the rules share, parsed on first use, and fourteen named rules run in the order the body ran them; the claims, their wording and the summary line are unchanged, and every copy-based case passed as it was.
`documentsFrom` holds the same interface over a map of path to text, and the two rules that run a process in the tree, the command surface and the release notes, say nothing where there is no tree.

## Status

**done** `scripts/check-docs.mjs` (`documents`, `documentsFrom`, `claims`, `context`, `RULES`, `checkDocs(root)`), pinned by `test/check-docs.test.mjs`: six cases over strings beside the copy-based ones, one on the single reading, and one holding the table's names.
The copy-based cases stay as the end-to-end layer; a case that wants one rule writes two strings now instead of a copy.
