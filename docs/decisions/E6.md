# E6

Section: E. Baseline and drift

## Decision

Drift is the files of the map the base changed since the commit it shares with the pin, whose bytes there differ from the pin's: a pinned file, or a source file the base added to a mapped area, with a rename counted once. Never `..HEAD`

## Why

Over HEAD the branch's own changes count as drift, so severity falls as the change under review grows.
The range between two commits is symmetric, which leaves the same hole from the other end: `anatomiya pin` puts the pin at HEAD, so pinning on a branch read the branch's own commits as a map that had moved.
Measured on a 12-file repository whose branch touched 6 mapped files: pin, scan, check reported "severity capped at FIX: 6 of 12 mapped files changed since the pin" against a pin that was HEAD, so a branch silenced its own findings by being large.
Drift is the base's own progress past what the pin already holds, and where the pin is a descendant of the base that is nothing.
Running from the shared commit alone opens the mirror of the same hole: after a squash merge the shared commit sits behind work the pin already holds, and a base whose tree is byte-identical to the pin reported 40 of 130 mapped files and capped again.
A path is drift when the base moved it since the shared commit and its bytes there differ from the pin's, which is both ranges at once.
One case is left standing and is worth naming: in a shallow clone `git merge-base` exits 1, the range falls back to the symmetric one, and a branch's own commits read as drift.
Reporting no drift there is worse, because an unmeasurable drift caps every finding at FIX permanently.
Counted over every path the range named, a base that edited ten JSON files beside twelve pinned sources read as 10 of 12 mapped files changed and capped every finding, though no claim counts a JSON file; and a pure rename of one of eight pinned files read as two changes, a removal and an addition, which is 0.25 and the cap. Counted over the map's own files, the same two read 0 of 12 and 1 of 8

## Status

**done** `git.mjs` (`resolveBaseRef`, the one resolver both phases read; `diffRange`, which also answers the paths the range added), `baseline.mjs` (`mergeBase` before the range, in `driftRange` and `laterOnBase`; `driftIn`, the count).
`driftIn` counts a changed path where the pin held it, or where the base added it, or renamed it in, and it is a source file (`isCorpusPath`); a fixture, a document or a generated file beside the code moves no count. A file the base added is read at the base first (`generatedAt` in `corpus.mjs`): one a generator stamped there, or a `linguist-generated` line in this checkout's root `.gitattributes` names, is no file of the corpus and moves no count, as the next scan's corpus drops it; read off the path alone, two such clients beside eight pinned sources were 2 of 8, the cap. A rename is charged once, in the area it went to, or where it was when it left every area. The check reads drift alone (`resolve` with `driftOnly`), so its staleness costs no identity read of the population.
`resolveBaseRef` throws where git could not be asked what a candidate names or for its merge base with HEAD, so neither phase measures to a ref's tip on a question nobody answered (F29).
`driftRange` and `laterOnBase` throw where the commit two histories share could not be asked for: read from the pin in its place, the range is the symmetric one and takes the branch's own commits for the base's, and a path the base added later reads as one the branch removed.
The check hands the resolver the base commit it resolved rather than the ref's name: a shallow clone's fetched base has no ref, and re-resolving the name capped every finding under "cannot resolve origin/main".
The commit handed over is the fork point where there is one, named explicitly, since the report's `base.sha` is the base ref's own tip
