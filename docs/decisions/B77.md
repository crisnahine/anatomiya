# B77

Section: B. Engine

## Decision

A child is listened to before its pipes are read, and the git reads keep their own clock

## Why

Measured on Node 22.22.3 in a helper with a descriptor limit of 64 and a process group of its own: with no descriptor left, `spawn` hands back a child with no pid and no `stdin`, `stdout` or `stderr`, queues `error` for the next tick and then raises `close` with the errno, -24.
`gitStreamed` read `child.stderr` first, so the promise rejected with a `TypeError` and the `error` after it had no listener, which ended the process at exit 1.
`startFor` read `child.stdout` inside the parent's handler of a thread's message, an uncaught exception that ended the scan.
`spawn`'s own `timeout` is never cleared for a child that did not start: Node attaches the listener that clears it to `exit`, and `exit` is emitted inside `spawn` before that listener is there, so with the listeners in order and the option kept the helper stayed up for the whole 120 s.
When that timer fires it calls `kill` on a child with no handle, which signals nothing.
A pipe that fails says so on the stream: with a child's stdout destroyed with an error and nobody listening, Node threw `Unhandled 'error' event` with `read EIO` and the process ended.
A signal alone does not end a git behind a launcher: the `git.exe` Git for Windows puts on the path starts the real git as its child with its pipes inherited and holds it in no job object, read in the launcher's source, so the signal ends the launcher and the git behind it goes on sending.
Measured with a stand-in behind a launcher: a walk its caller had ended had not settled at the test's 60 s, since `close` waits on the pipes, and neither had a read past its clock; with the pipes shut at the signal both settle, and a stand-in that writes stops at its next write.
Measured on Windows (Git for Windows 2.55, on CI) with real git over 80,000 generated commits: with the pipes left open, a read its 300 ms clock ended settled after 2032 and 1632 ms, the git behind the launcher sending on, and with them shut after 305 and 309 ms.
With the pipes shut, a git that exits 0 as the clock runs out has left part of its listing unread: a stand-in's read the clock had ended answered one of its three records, so a read its clock ended is no answer whatever the exit code.
Node's `execFile` has the same hole, since it shuts the pipes at its own timeout and answers with the code a child left in that moment: a buffered read of a stand-in's three records answered `ok` with one where it exited 0, and `code: 1` where it exited 1, which a caller reads as git saying no.
Where git exits 0 the caller cannot tell from what it is handed: Node hands it no error, and the child's own `killed` is set only where the signal reached a live child, so a child already reaped, or one Windows calls already dead, leaves it false.
Deciding by the time a read took is no way out: Node keeps its loop clock in whole milliseconds, so a timer fired up to about 1 ms before `performance.now()` said its time was up (11 of 2000 5 ms timers on Node 22.22.3 on macOS, the earliest at 4.051 ms).
The read of which commands a repository's config names went through Node's `timeout` too, and a part of its answer read as the whole leaves a command the cut-off part names with nothing to keep it from running.
An option Node refuses is thrown from `spawn` itself: a NUL in the environment gave `ERR_INVALID_ARG_VALUE` before any child was there

## Status

**done** `git.mjs` (`gitStreamed`, `gitBuffered`, `runOnClock`, `spawnGit`, the one start of a git child the streamed reader and the batch blob reader share, and `endChild`, the one way either ends one, so the launcher fix that landed twice in a day lands once), `ruby.mjs` (`startFor`, `onThread`, `parseBatch`), `child.mjs` (`signalChild`), pinned by `test/git.test.mjs` (`a streamed read with no descriptors left for its git is rejected as a git that failed to start`, `a streamed read whose pipe fails is rejected, and the failure ends no process`, `a streamed read whose start throws is rejected as a git that failed to start`, `a streamed read that never returns is ended by its own timeout`, `a walk its caller ended does not wait on a git behind a launcher, and that git stops`, `a streamed read behind a launcher is ended by its own timeout too`, `a listing whose git exits as its clock runs out is no answer, however it exited`, `a long walk its clock ends settles near the clock, whatever starts git`, `a buffered read behind a launcher is ended by its own clock too`, `a configuration read whose git was reaped before its clock ran out is unasked too`, `a timeout that is no whole number of milliseconds is refused rather than run with no clock`, `a batch reader given a timeout that is no whole number of milliseconds asks git nothing`) and `test/ruby.test.mjs` (`a child with no descriptors left to start on tells its thread, and every call the thread makes on it is safe`, `a child's pipe that fails tells its thread, and the failure ends no process`, `the files of a batch whose child had no descriptors to start on are charged, as they are for one that could not start`).
`gitStreamed` attaches the child's `error` listener before it touches a pipe and reads each pipe only where the child has one, so a child that never started rejects the read with `git <subcommand> failed: <the system's message>`.
A start that throws rejects with the same words.
Its clock is a timer of its own that sends `SIGTERM` through `signalChild` (B76), is cleared on `close` and on any failure, and is unreferenced, so a clear that is missed holds no process open.
The clock and the caller's stop shut the child's stdout and stderr with the signal, so a read behind a launcher settles when the launcher has gone and a git behind it stops at its next write; one that writes nothing is not ended.
A read its clock ended rejects with `git <subcommand> exited SIGTERM` whatever code the child left.
`gitBuffered` and the read of which commands the repository's config names start git through `runOnClock`, a clock of its own in place of Node's `timeout`: at the clock it shuts the pipes and sends `SIGTERM`, and a read it ended is no answer whatever code the child left, from `gitBuffered` not ok with no exit code (`a buffered read whose git exits 0 as its clock runs out is no answer either`, and the same with 1) and from the other a configuration git could not be asked about, which refuses the call (`a configuration read whose git exits 0 as its clock runs out leaves the call unasked`, the same with 1, and `a configuration read whose git was reaped before its clock ran out is unasked too`, where the signal reaches no live git), each failing without its check.
A buffered or a streamed read given a timeout that is no whole number of milliseconds from 0 to 2^31 - 1 is refused, as Node refused one below 0, NaN or a fraction for the buffered one, since one below 0 or NaN would run with no clock and Node cuts one past 2^31 - 1 to 1 ms (`a timeout that is no whole number of milliseconds is refused rather than run with no clock`); 0 and null mean no clock there, as they did for Node.
A batch reader given one below 0, NaN or a fraction asks git nothing and hands each file to the buffered read (`a batch reader given a timeout that is no whole number of milliseconds asks git nothing`), and given 0 or null it drops its child after 1 ms and hands each file to the buffered read, which runs with no clock.
A stdout that errors rejects the read, since half of stdout is no answer, and a stderr that errors is passed over, since stderr only words a failure.
`startFor` attaches `error` and `close` directly after the start, reads each pipe only where the child has one, and gives the thread `read()` and `input()`, both safe on a child with no pipes.
A stdout or a stderr of that child that errors is posted to the thread as the child's own error is, and the child is ended through `signalChild`; the thread fails the batch and its files are charged as crashed.
`parseBatch` reads its child's pipes with no such guard and throws without a `spawner`, so the one child it reads is the stand-in a thread makes, which always has its streams.
Every other start in the library that reads its own pipes is behind `guardedChild`, is `blobReader`'s (E17) or is `gitStreamed`'s, and the refresh worker's is started with every stdio closed (A95).
The `execFile` starts hand their pipes to Node: `gitBuffered` and the configuration read in `git.mjs`, and the ones in `pool.mjs`, `ruby.mjs`, `readiness.mjs` and `commands.mjs`
