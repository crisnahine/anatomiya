# E17

Section: E. Baseline and drift

## Decision

Every blob read at a revision goes through one `git cat-file --batch -Z` child for each `readAtRevision` call. The per-call reader, `git cat-file blob`, is its only fallback and answers whatever the child cannot, and the child never fetches

## Why

One process per blob was 297 of the 310 git processes a check of 246 changed files started on this repository; with the one child that check starts 15, two of them the batch children of its base and its head.
A check of 30 changed files went from 66 git processes to 15.
The check of 246 files took a median 31.9 s before and 20.7 s after, five interleaved runs at a load average near 150.
`-Z` ends each request and each reply with a NUL, because line input cannot carry a path holding a newline and drops a carriage return at a path's end.
Never `--buffer`, which holds a reply back until stdin closes, so no reply could be read before the next request is written.
`-Z` came with git 2.42 and Debian 12 ships 2.39, so stating 2.42 as the least git lost to falling back: a child that cannot be started, exits, breaks the framing, errors on a pipe or outlasts the caller's timeout on one request hands that read and every later one to the per-call reader.
No answer changes for it: on git 2.39.5, in a container, the reader's tests passed through the fallback, 99 of them, with the 4 that count on the one child answering skipped.
The size is in the reply's header, so a blob over the size the parser reads is refused before a byte of it is read, and that child is ended so the body is never pulled through the pipe.
Ending it takes shutting its output as well as the signal: the `git.exe` Git for Windows puts on the path is a launcher that starts the real git as its child with its pipes inherited, waits for it and holds it in no job object, read in the launcher's source, so the signal ends the launcher alone.
Measured with a stand-in behind a launcher: with the output left open it never stopped sending, and with it shut it stops at its next write.
On Windows, with the output left open, both test legs failed to remove a repository after a read over the cap, `EBUSY` on Node 22 and `EPERM` on Node 24: something still held its directory.
That the launcher is what held it was run on no Windows machine apart from those legs; `test/git.test.mjs` (`a repository is free to be removed once a reader that refused a reply has closed`) holds the loop from the read to the removal, so it passes there only where the git behind the launcher lets go with nothing more read.
The reply's type is checked, since `<sha>:<directory>` answers with a tree where `cat-file blob` errors.
The child runs with lazy fetch off whatever the caller asked, because it answers one request at a time and would fetch a blobless clone's missing blobs in turn: 60 blobs from a local promisor took 4.3 s that way, against 1.2 s for eight `cat-file blob` processes side by side.
So where the caller asked for a fetch, each reply of `missing` goes to the per-call reader under `readAtRevision`'s pool of eight, and the child stays up for what the clone holds: 1.1 s for the same 60 blobs, medians of five interleaved runs.
A gitlink is answered with `<object id> submodule` and neither the request nor a size: measured on git 2.54.0, `printf 'HEAD:sub\0HEAD:gone\0HEAD:a.ts\0' | git cat-file --batch -Z` prints forty ones and `submodule`, then `HEAD:gone missing`, then the blob.
Read as broken framing, one gitlink sent every later read of that revision to the per-call reader: four reads started four processes where one child answers them.
Given up: a stalled git costs the read in flight the caller's timeout twice, once in the child and once in the per-call reader; and a fetching read of a base path that is truly absent costs one more process, which the check never asks for

## Status

**done** `git.mjs` (`blobReader`, `showBlob`, `FLAGS`), `revision.mjs` (`readAtRevision`), `check.mjs`, `baseline.mjs`, pinned by `test/git.test.mjs` (`a gitlink is absent, and the reads after it are still answered by the one child`), `test/revision.test.mjs` and `test/check.test.mjs` (`check spawns two cat-file children for a base and a head`).
`blobReader(root, sha, { timeout, env, lazyFetch, closeGrace })` answers `read(path)` as `showBlob` answers it, and a read never rejects.
A request is `<sha>:<path>` and a NUL on the child's stdin, one in flight at a time; a path holding a NUL goes to the per-call reader.
A reader whose sha is malformed starts no child.
A reply that is the request and one word, `missing` among them, answers `absent`, or goes to the per-call reader where the caller asked for a fetch.
A gitlink's reply, an object id and `submodule`, answers `absent` as the per-call reader does, and the child is kept for the reads after it.
A reply whose type is not `blob` answers `absent` and one over `MAX_FILE_BYTES` answers `over size cap`; either ends that child, and the next read starts another.
The child is started on the first read, with the repository's commands closed as for every git call (F5) and `GIT_NO_LAZY_FETCH` set.
`close()` ends the child's stdin, gives it `closeGrace`, one second unless given, to leave before it is killed, and waits as long again for each child the reader killed.
A kill is sent through `signalChild`, only to a child with a pid (B76).
The child's output is shut before the signal.
A test that needs the one child to answer is skipped on a git older than 2.42 through `needsBatchZ` in `test/platform.mjs`, which is an avoidable skip.
`docs/research/what-git-cat-file-batch-reads.md` holds what git prints.
A read that ended with no exit code and was not over size answers `{ ok: false, reason: "unasked" }` with `git could not be asked for <path> at <sha>` and what ended git as `error`, and `readAtRevision` carries both in `missing`.
A blob that could not be read is not absent: the baseline stops on one (`countAtPin`), and the check says so in a caveat naming the file.
A path holding a NUL answers `absent` without asking, since Node refuses the argument and no tree names such a path.
`blobReader` hands a read its child could not answer to `showBlob`, and the read is `unasked` only where that could not ask either
