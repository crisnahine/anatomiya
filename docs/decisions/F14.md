# F14

Section: F. Safety

## Decision

On a partial clone the author pass uses `-M100%`, and no git read lazy-fetches except the check's reads of the merge base

## Why

Measured: `-M` scores similarity, which needs blob content a `--filter=blob:none` clone does not hold, so git fetched from the promisor one round trip at a time.
33 of 35 measured clones could not answer at all and reported history unread; warming them cost 62 seconds to 57 minutes each and 4 GB of network.
A full clone is untouched and keeps the inexact detection D5 was measured on.
Every read sets `GIT_NO_LAZY_FETCH` (`git.mjs` `gitEnv`), so a pinned blob the clone lacks reads as missing instead of reaching the network.
The check's reads against the merge base are the exception (`lazyFetch`): its blob read, and its diff of the changed files, whose rename detection reads the base side of each added and deleted path.
A branch checked out without the base ever held has none of the base's blobs; every changed file was skipped with nothing found, and a branch with an edited rename had its whole diff refused.
They ask for the changed paths alone, from the clone's own promisor, bounded by the check's git clock (`test/check.test.mjs`).
A repository naming its own `remote.<name>.uploadpack` gets no lazy fetch at all, since the fetch would run it (F5)
