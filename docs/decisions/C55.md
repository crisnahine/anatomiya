# C55

Section: C. The counted-claim model

## Decision

A co-change claim says what a change adding a file of one class also touches: one named file edited, or a file of another class added. Counted over first-parent changes on the default branch up to the pin, the newest 20,000, each producer class over its newest 100 candidates. A path this tool writes is no part of a change on either side. Stored in the record's `layout.cochange`, at most 100 stated claims and 100 near misses, rendered after the directives of the producer's area, enforced by `check` and said by the notice

## Why

Nine fixed spec pairs cannot say that a new cop is entered in `config/default.yml` or that a component ships with a changeset, and no count over the tree sees it: the evidence is which files changed together.
Measured on 44 repositories with the build's own walk and gates, mined on the older four fifths of the changes read and held out on the newest fifth: 24 claims in 11 repositories, and 1,563 of 1,633 held-out candidates conformed (95.7%); mined over every change read, which is what a scan states, 25 claims in 9 (`docs/measurements/2026-10-11-cochange.md`).
Of the 25, 16 print in an area file; 9 print nowhere, a parent class spanning sibling areas or a producer kind its area's globs do not reach, and the notice and the check still say them.
First-parent, because the check's unit is a branch and a branch lands as one first-parent change.
20,000 rather than 4,000, because the Wilson bound needs 35 candidates and 4,000 found 10 claims in 5 repositories; the per-class cap, because a deep window buries a recent habit (rubocop's style cops ship with an edit to `config/default.yml` 77 of 77 times in its newest 4,000 counted changes and 200 of 334 times over all 11,773 it has).
The map's own files are left out because an untracked or refreshed map counts among a branch's files and pushes it toward the 40-file bound, and a repository that commits its map would mine a claim that a new file ships with an area file
