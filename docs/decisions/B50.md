# B50

Section: B. Engine

## Decision

Each Ruby shard runs in a worker thread that keeps its child's clocks and retry, decodes and parses the stream and answers the rows, so no tree is parsed or walked on the parent and one record per file crosses back (counts for a scan, the tree only for the check's touched files). This replaces B48's contiguous batches

## Why

The child is started on the parent at the thread's request and its bytes relayed undecoded, the child paused while four chunks wait on the thread, and a thread that ends without its final answer has every child it asked for killed and reaped before its batch is read again or charged.
The shards are balanced by bytes, the largest file first into the lightest shard, an equal load to the shard holding fewer files, a file over the size cap weighing nothing since the child skips it unread, and the records are put back in input order before anything reads them.
The 500-file floor, each child's clocks and retry and every failure's text are unchanged; the cap on shards stays four, never more than the pool size.
On a dying child, which files it charges moves with the byte balance: the count and the text are what contiguous batches gave, and the files named may differ, because charging the same files needs the contiguous batches this row removes.
On a large corpus the map moves with them, as well as the files named: its areas, stated claims and barren files can differ too.
A check's tree crosses to the parent as JSON text the parent parses, as 0.13.3 read every tree off the child's line: decoding a deeply nested object off a message overflows the parent's stack, and a 700-deep nest of blocks was lost as a false head-unparsed.
Any file left with no record when a shard answers is charged as crashed.
The idle clock also measures how busy the parent is, since every chunk and every backpressure acknowledgement passes through the parent's event loop.
Each thread's heap is held to 16 MB plus 32 MB per MB of its largest file, or 16 MB plus 96 MB per MB where that file is past 256 KB, and a thread that runs out of that hold keeps the records it posted, and only the files it left unanswered are read again on a thread with the default heap.
A thread that ends any other way without its final answer charges its whole batch and discards what it posted.
On 0.13.3 the parent read and walked every Ruby tree, and the last of four contiguous shards finished well after the first.
Measured on a Rails API under the bench lock, 0.13.3 against this build, from the parse's start to its answer, median of five: the parse phase went 3,378 ms to 1,820 ms; on discourse 12.5s to 6.6s and on canvas-lms 19.7s to 10.0s, median of three, every language's parse included.
V8 grows a heap toward its limit rather than its live set, so four threads at the default limit nearly doubled peak memory; held, with the parent passing each chunk's memory to the thread rather than a copy and pausing the child at four chunks in flight, the API's peak stays within about a sixth of 0.13.3's (measured below).
A flat 16 MB hold sent six threads on discourse and canvas-lms back for a second read, slower than before: a 588 KB spec needs 20 MB of old generation, and a thread that held every record of its batch outgrew the rest.
So the hold follows the largest file and each record leaves as it is decided, and on the corpus's 19 Ruby repositories and microsoft/vscode, which holds 5 `.rb` files, no thread ran out of its hold.
Dense code needs more: generated files of nested calls and nested hashes needed 28 MB of old generation at 256 KB and 90 MB at a megabyte, against 15 MB for a megabyte of one-line `def`s, so a 1 MB file of them ran out of a 40 MB hold and was read twice, 10.5s against 5.6s on 0.13.3.
A hold covering them on every thread took a measured Rails API's peak from 221 MB to about 340 MB, since V8 fills what it is given, so only a shard whose largest file is past 256 KB gets the larger hold: the API's largest is under 256 KB and its peak did not move (226 MB against 229 MB with six shards, medians of three, 0.13.3 192 MB; at four shards the larger hold on every thread would be 228 MB against 194 MB, 0.13.3 180 MB, so it stays on the shards past 256 KB only), discourse and canvas-lms, whose largest pass it, stayed at 453 MB and 506 MB, the 1 MB file read once, and every shape built from 260 KB to the cap read once.
Below 256 KB a dense file can still outgrow the hold and is read twice, which costs little at that size.
The smaller hold starts at 16 MB because a thread that has loaded its modules and read no file already uses 7 to 8 MB: on Linux x64 a base of 8 MB ran out on half the thread startups before any Ruby was read, each batch then read again on the default heap, and one such startup aborted the whole process; at 16 MB, 16 of 16 startups held.
The cap of four came from discourse while the parent walked every tree, where a fifth and sixth child gained little (12.8s against 13.5s).
With the shards walking, six beat four on time, 4% to 16% less scan wall on a measured Rails API and 4% to 11% on discourse, but each shard thread holds a heap of its own and six put the API's peak 22% to 30% over 0.13.3's in every harness, so the cap stayed four.
Measured on the CLI (`/usr/bin/time -l` on `scan --dry-run`, bench lock, five alternating runs each at load 1.4 to 5.7, medians), the API's scan takes 2,260 ms against 0.13.3's 3,900 ms, and its peak is 206.6 MB against 178.0 MB, 16.1% more (0.13.3 176.7 to 183.1 MB, this build 200.4 to 212.4); discourse's scan takes 7.6s against 13.8s at 453 MB against 456 MB.
The plan was byte-identical before and after on those 20 and on this repository.
A thread rather than a process because nothing here can crash the way an oxc parse can (B2): prism runs in the child.
The parent owns the child because only the thread that spawns a child can reap it: started on the thread, a child whose thread ran out of heap kept parsing beside the rerun's child with no clock on it, then stayed a zombie until the scan exited
