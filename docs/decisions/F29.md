# F29

Section: F. Safety

## Decision

A git that could not be asked is no answer: a call that ended with no exit code decides nothing, and where reading it as "no" would let the tool write, move a pin or state something about the repository, the scan, the pin or the check stops with the question and git's text

## Why

`gitBuffered` answers `code: null` for a clock that ran out, a signal, a start that failed, an argument it refused and a configuration nobody could read, and `shaReachable` and `commitAt` read that as "the commit is gone" and "the ref names nothing".
Measured with a git ended by a signal: a scan dropped to counts and said the pinned commit was gone from the repository; the refresh worker read a pin as a first pin and skipped the guard that keeps it from moving back; a pin stopped with "this repository has no HEAD"; a co-change walk wrote a map with no claim and no error; and a check with HEAD unasked let a `--base` naming nothing pass at exit 0.
Eight more reads had the same shape: whether the pin is newer than HEAD (the pin moved back), who this clone commits as (its own commit was pinned), whether the map is committed (the worker wrote over a tracked map), whether the repository folds case, whether the clone is shallow (a window read as the whole history states the claims D11 refuses), how the remote's branch last moved (a clone that had pulled read as `not-fetched` or `no-record`), which ref a typed base names (a base that looks like a commit id and equals HEAD's commit passed as one), and the merge base (the check printed "no merge base" at exit 0, and the scan measured drift to the ref's tip).
Exit codes, measured the same on git 2.54.0 and on git 2.39.5: `rev-parse --verify --quiet <x>^{commit}` exits 0 for a commit named by a ref, a full sha or a short one; 1 for a name or a sha that is not there, for a tree, and for HEAD in a repository with no commit; and 128 in a directory that is no repository.
`cat-file -e <x>^{commit}` exits 128 for every one of those but the commit, so its exit code cannot tell "not there" from a git that refused.
So whether a commit is there and which commit a ref names are asked with `rev-parse`: 0 is yes, 1 is no, and any other exit code throws as a missing one does.
`rev-parse --verify --quiet` also exits 128 with nothing printed for a name it refuses, such as a reflog entry past the log's end (`HEAD@{9999}`): `commitAt` reads that as a name that is not there, so `check --base 'HEAD@{9999}'` says the base resolves to no commit, a 128 with text still throws, and `shaReachable` reads no 128 as gone.
A reader of anything else answers a call with no exit code one of two ways: `filesAt`, `changedSinceWorktree`, `diffRange` and `mergeBase` throw, and `showBlob` answers with the reason `unasked` and leaves it to its caller.
A call that ended with an exit code is git's answer, but for two: `mergeBase` where git fails with an exit code other than 1 for two names that are both commits, since a name that is no commit ends with such a code too and a caller reads a failed merge base as that, and a read its clock ended, since the pipes are shut at the clock and a git that exits 0 in that moment has left part of its answer unread (B77).
What a caller does with a read that could not be asked is one of three: stop, say so in what it prints or records, or do nothing, and no read is left unruled.
Measured on `rootAttributes` in `corpus.mjs` with a skip-worktree `.gitattributes` and the read ended by a signal: a file the index's attributes mark generated was counted as source, and nothing said so.
Run with a git that dies on every call, five of the seven hook events `hooks.json` registers were run, and each exits 0 with valid JSON and an empty stderr: the hook boundary answers `{}` for any throw, and the one throw a hook's own read reaches, for a checkout's attributes in the stop hook, is caught there so that checkout asks nothing and the others are still read (`pendingChange`).
Given up: a repository git can open only part way, such as an object store that answers 128 to `rev-parse`, stops the scan, the pin, the check and the refresh worker with git's text, where it read as "no commit" before.
Given up: a question waits out its clock before it throws, 120 s for most and 30 s for the check's own reads of HEAD and of a ref's name, and a refresh worker that ends on one records nothing, so each later trigger asks again and can wait as long.
Given up: one read of the check does not stop it, the fold it asks while it rebuilds a corpus the record lacks, which becomes a caveat carrying git's text

## Status

**done** `git.mjs` (`Unasked`, `answered`, `yesOrNo`, `failureOf`, `shaReachable`, `commitAt`, `headSha`, `caseMagic`, `mergeBase`, `resolveBaseRef`), `baseline.mjs` (`resolve`, `laterOnBase`, `driftRange`), `authors.mjs` (`shallowHistory`, `authorsByFile`), `cochange-walk.mjs` (`cochangeTip`, `startCochange`), `check.mjs` (`resolveBase`, `staleness`), `commands.mjs` (`runPin`, `refuseMoved`), `refresh-run.mjs` (`refreshRepository`, `followPin`, `committerEmail`, `fetchedHere`, `clonedOnto`, `mapTracked`, `committedTargets`), pinned by `test/git.test.mjs` (`a git that refused is not a git that said no: only exit code 1 is`), `test/baseline.test.mjs`, `test/authors.test.mjs`, `test/cochange-walk.test.mjs`, `test/commands.test.mjs`, `test/cli.test.mjs` and `test/refresh.test.mjs`.
A call could not be asked where it has no exit code, and `answered` throws an `Unasked` for it; `yesOrNo` throws the same for an exit code other than 0 and 1.
A read its clock ended has no exit code to read, whatever code git left: `gitBuffered` answers `code: null` for it and `gitStreamed` rejects with an `Unasked` (B77).
The message is `git could not be asked <question>: <why>`, and the why is git's own text, or the signal and the clock that ended it, on one line (`failureOf`).
Three answers each, a yes, a no and the throw: `shaReachable`, `commitAt` with `headSha` through it, and `caseMagic`, where exit code 1 is a key that is not set.
`mergeBase` keeps its three outcomes and throws an `Unasked` where it failed with no exit code, and where it failed with an exit code other than 1 for two names that are both commits.
`resolveBaseRef` throws where a candidate could not be asked about.
`commitAt` answers null for an exit code of 128 with nothing printed, and throws for a 128 with text.
A scan stops with the message, writes nothing and exits 1: `resolve` throws for whether the pinned commit is still here, for what a base ref names, for its merge base, and for the two forks `laterOnBase` and `driftRange` ask, and the corpus read throws for the fold where it asks it.
It stops the same way for the files the pin or a fork held (`filesAt`), for what changed since the pin (`diffRange`), for the files that differ from the pin (`changedSinceWorktree`) and for a pinned blob (`countAtPin`, E17).
A pin stops the same way where HEAD could not be asked, before the list is read or after it, and writes no pin.
It stops too where `refuseUnlikeHead` could not ask whether the index holds unmerged paths, whether a merge is in progress or whether the working tree matches HEAD, and where its listing of the index could not be read, and a refresh worker that pins ends there.
A check stops and prints no report where it could not ask for HEAD, for what a base names, for which ref a typed `--base` names, for the merge base, the one after its shallow fetch included, or for the pinned commit.
It stops the same way for whether the clone is shallow, which refs hold the name of a typed base, which parents HEAD's commit records and the oldest commit the clone holds (`askGit`), and for the tracked tests (`trackedTests`, `placedAmong`).
A read of the check that could not be asked and does not stop it is a caveat in the report: the diff, the added ranges, the pending edits, the shallow fetch, the directories at the merge base, the tree listings the obligations read, and a blob at HEAD or at the merge base, with the file named (F15).
`no merge base between <ref> and HEAD` is printed only where git ran and found none.
A shallow probe that could not be asked is unread history: `authorsByFile` starts no log and carries the message as `error`, a repository with no commit included, so every author gate fails with that reason (F13, D11); the count and the root asked after it stay soft.
A co-change tip that could not be asked for is a walk that failed: the record carries the error, the summary prints it, no co-change claim is stated, and the scan goes on (E16).
The refresh worker ends where a question before its stamp could not be asked: `refreshRepository` rejects with the lock let go, the pin, the map and `refresh.json` as they were and nothing recorded, the process exits 1, and the next trigger asks again.
Those questions are whether the map is committed and the fold read for it, HEAD, the remote's tip, whether the pinned commit is still here, whether the pin is the newer one, and any read the pin itself makes.
A question that could not be asked after the stamp is read, the fold `committedTargets` asks and any read inside the scan, is a failed refresh of that stamp: `refresh.json` records `ok: false` with the message, and the same stamp waits out the 30 minutes (A95).
Two questions are held as `unread` and end nothing: how the remote's branch last moved (`fetchedHere`, `clonedOnto`) and who this clone commits as (E11).
`mapTracked` throws on any listing git did not give, an exit code or none, since `ls-files` has no exit code that means nothing is tracked.
The memory in front of `commitAt` and `mergeBase` keeps no throw (E14).
`test/modules.test.mjs` (`every read of a git result outside git.mjs goes through answered or is on the list of what it does unasked`) lists every raw read of a git result by file and function with what it does (`RAW_GIT_READS`): it says so, it does nothing, or it throws on every failure, and a read in a function the list lacks fails the test.
The list holds no open entry: both reads of `rootAttributes` in `corpus.mjs`, how the index marks `.gitattributes` and the index's copy of it, go through `answered`, so a git that could not be asked stops the scan with git's text, and the stop hook, which reads every checkout of a stop together, asks nothing about that checkout (`pendingChange`)
