# C66

Section: C. The counted-claim model

## Decision

No wiring check and no row over a pipeline file is built: an i18n key's presence in the base locale, the content of data-definition files and Dockerfiles, a workflow's extension, and an action pinned to a sha were measured and refused. A migration that ships with its schema edit is already a co-change claim (C55); the half of `schema_matches_migrations` that reads what the schema diff holds stays planned

## Why

#243 asked for these to be measured, read-only over the corpus (`docs/measurements/2026-10-23-unread-classes.md`).
An i18n key used in code exists in the base locale: a correctness check with no sides for a ratio. Where the mapping from call to locale file is simple, 29 of the 33 slots with 20 literal keys already find 0.90 or more of them. Where it would fire, 28,237 of 28,322 keys not found (554 of 639 without canvas-lms) are a mapping it did not follow (lazy paths, a `scope:`, i18nliner, a namespace), not a missing key, and in 6 of the 16 repositories read a missing key already fails a spec, a CI job or `tsc`.
A migration ships with a schema edit: co-change states it already, in 4 of the 14 Rails repositories (whitehall 97 of 100, consul 100 of 100, forem 99 of 100, mastodon 99 of 100), and 4 more stop at a measured gate (openfoodnetwork 91 of 100 and a measured Rails API 57 of 60 in a shallow checkout at the evidence gate, diaspora at `exists` since it stopped tracking `db/schema.rb`, and discourse at the ratio, 35 of 100, since it tracks `db/structure.sql` again only from 2026-05-14), as does mastodon's `db/post_migrate`, 41 of 42 at evidence. Six commit no schema, so there is nothing to state. That the schema changes only what the branch's migrations produce is a branch invariant, a new kind and a reader of the schema and the migration DSL, and was not measured.
Data-definition files: GraphQL in 3 repositories and Prisma in 3, one reaching 20 files, too few for a ratio; SQL is migrations, which co-change reads by class; a Dockerfile's `FROM` pinned by digest holds one side only, a tag, in 5 of the 6 repositories with 20 lines at 0.90.
A workflow's extension: the 13 repositories with 20 workflows all hold `.yml`, 0.9333 to 1.0000, none under the gate.
An action ref pinned to a sha clears the numbers: 56 repositories with 20 `uses:` sites, 28 hold sha and 26 a tag, spread 1.0. Then 3 sessions with no map on backstage, which pins 244 of 244, one model and one effort (G11): 12 of 12 refs written pinned with the siblings' own sha and `# vX` comment, each after reading sibling workflows. Half the sha holders (14 of 28) also run zizmor, pinact, ratchet or harden-runner, whose `unpinned-uses` audit is this check, and a workflow is no source file, so it has no area to sit in

## Status

**done** Nothing is built.
`docs/dimension-intake.md` holds a dropped row for `i18n_key_exists` and `action_pinned_sha`, and `schema_matches_migrations` stays planned there. A workflow's extension is the YAML extension `yaml_extension` drops (C64), and the GraphQL, Prisma and Dockerfile counts are too few or one-sided to name a row, so this row and the measurement note are their record.
A barrel index was measured in the research note: 17 repositories have 20 or more barrel sites, 2 hold "a barrel re-exports every sibling", and a barrel is complete in 0 of 9 at 0.90, so it is no habit a row could state.
Not measured: i18n in `.vue`, `.svelte`, `.gjs` and `.hbs` templates; other one-file registries such as a plugin or command list, which differ by project and name no construct a row could count; and a workflow needing an action no sibling workflow uses, the one case the sha sessions did not reach
