# B49

Section: B. Engine

## Decision

A row is a visitor of one walk per file, `walk` for JS, `walkRuby` for Ruby and `walkTree` for a tree-sitter tree. A throw in one row drops that row's sites for the file and no other row's

## Why

`collectHits` makes every visitor row's visitor, takes one walk, and hands each node to each live row, then calls each row's `done`.
A throw while making a visitor, on any node, or in `done` drops that row's sites for the file and no other row's; a throw from the walk itself drops every visitor row's sites for the file, and a row with its own `run` keeps its own.
`dimensions.mjs` sets every visitor row's `run` to `fromVisitor` on its engine's walk, so the check and the tests still ask one row at a time.
The Ruby facets ride the same walk as a visitor in `collectHits`'s `also` list: fed whether or not any row was asked for, and a throw, theirs or the walk's, is held in their `error` and thrown by their `done`, which the bridge answers with no test runner, never costing a row its sites.
A JavaScript file's facets take their own walk first, because they choose its rows, and only the rows they choose go on the shared walk.
A walk here is one call of `walk` or `walkRuby`, on a file's tree or on a subtree inside it, over the files that engine parsed, and a callback is one call the walker makes to its visitor.
Measured on private client, 0.13.3 against this build: every row started its own walk, 50.8 walks and 18,518 callbacks a file, and `collectHits` was 87% of each parse worker's `parseFile` time.
One shared walk took that to 9.2 walks (the facets' walk, the shared one, one import walk the three routing rows share, one walk for `jsxElementNames` where a site depends on it, and the subtree walks rows take inside one node) and 2,047 callbacks a file.
Summed over the workers, `collectHits` went from 13.6s to 4.3s (5.47ms to 1.72ms a file) and its share from 0.87 to 0.67, medians of three at load 11 to 14.
On this repository a file went from 83.6 walks to 46.8, most of what is left being subtree walks inside function bodies.
Client's scan barely moved (12.7s and 12.2s, medians of five), because the checker sets it.
A row's sites keep the order and content its own walk gave, and what needs the whole file is judged in `done`: `error_shape` still adds every throw before every result, and `spread_on_component` judges each spread against every name the file forwards.
`handler_memoised` keeps only the functions above each passed handler, since a binding's scope is always one: a copy of every ancestor grew with depth squared, and on 15,000-deep JSX this build peaks at 156 MB against 0.13.3's 161 MB, with the same hits.
The plan hash was identical before and after on all 35 corpus repositories and this one.
The fifteen Ruby rows became visitors of one `walkRuby` the same way, and the Ruby facets ride it too, so on rails-api a Ruby file went from 22.5 walks and 5,195 callbacks to 5.5 and 433 (the shared walk and the subtree walks rows take inside a class or method), with the plan hash identical on all 35 corpus repositories and this one.
A Ruby batch's rows are chosen from its languages and frameworks before any file is read, so its facets choose no row.
A JavaScript file's facets are the other way round: which rows they allow is known only after their walk, which costs 502ms of `parseFile` beside 4,269ms of rows over client's 2,486 files.
A file walks 25.0 rows on this repository and 30.2 on client.
A build that folded the facets into the shared walk, measured against the same build without the fold, had every row a file could get walk, all 32 a JavaScript file can get, and on this repository its parse workers' CPU rose 9% (3,166 to 3,459ms summed over the workers, median of five) with the scan's wall flat; on client the CPU was flat.
So the JavaScript fold was taken back; no row reads another's sites

## Status

**done** `walk.mjs` (`collectHits(program, dimensions, extra, { walker, also })` takes the walker, defaulting to `walk`, and the `also` visitors in one options object, and feeds rows and riders from one list; `fromVisitor(visitor, walker)` takes the walker too; the Ruby bridge passes `walkRuby`), `dimensions.mjs` (`WALKS`, `engineOf`: one loop sets every visitor row's `run`), `facets.mjs` (`jsFacets` walks for itself and answers the facets; `rubyFacets` returns a visitor whose `done` answers them, or throws the error the walk left it holding; a JavaScript file's facets still choose its rows, as `test/parse-file.test.mjs` pins with a JSX row a `.ts` file never makes), `ruby.mjs` (`take`), every walking row in `dimensions-base.mjs`, `dimensions-extra.mjs`, `dimensions-jsx.mjs`, `dimensions-naming.mjs`, `dimensions-capability.mjs`, `dimensions-ruby.mjs`, `dimensions-rails.mjs`.
The two Ruby rows that skip a Sidekiq `perform` collect the include on the same walk and decide in `done`, since it may sit below the def.
`jsxElementNames` is kept per tree in a WeakMap and asked only when a site depends on it; the routing rows share the tree's import list the same way, because each asks `wrapperBindings` with its own vocabulary.
`hook_per_module`, `exported_class_case` and `exported_type_case` read `program.body` and never walked, so they keep `run`.
No row spans two engines, so a row's first language picks its walk.
Visitors share one ctx per node and must not write to it: `test/walk.test.mjs` runs every JS row with each ctx frozen and holds the shared walk to each row walking alone, and `test/ruby.test.mjs` and `test/dimensions-rails.test.mjs` do the same for every Ruby row.
B47 holds: `ctx.within`, `fn` and `cls` are unchanged
